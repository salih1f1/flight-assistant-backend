# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Quick Start

```bash
# Start dependencies
docker compose up -d   # PostgreSQL 16 on :5432, Redis 7 on :6379

# Run API (Swagger at http://localhost:5100/swagger)
dotnet run --project FlightAssistant.API

# Apply migrations locally — design-time EF reads CONNECTION_STRING, not appsettings
CONNECTION_STRING="Host=localhost;Port=5432;Database=flightassistant;Username=fa;Password=fa" \
  dotnet ef database update --project FlightAssistant.Infrastructure --startup-project FlightAssistant.API
```

## Architecture

ASP.NET Core Web API using **Clean Architecture + CQRS** (MediatR) with **Domain-Driven Design**.

**Layers:**
- `FlightAssistant.Domain` — Aggregates, entities, domain events, value objects, exceptions. Private constructors everywhere; use factory methods.
- `FlightAssistant.Application` — MediatR command/query handlers + FluentValidation validators. All use cases live here.
- `FlightAssistant.Infrastructure` — EF Core + PostgreSQL, Redis, HTTP clients for external APIs, APNs.
- `FlightAssistant.API` — Minimal API endpoints, middleware, DI wiring in `Program.cs`, hosted services.
- `FlightAssistant.Contracts` — Request/response DTOs. No dependencies on other layers.
- `FlightAssistant.SharedKernel` — Currently empty; base classes live in `Domain/Common/` instead.

**Bounded contexts:** Travelers, Flights, Loyalty, Lounges, Configuration (reference data).

## Domain Base Classes

All live in `FlightAssistant.Domain/Common/`, **not** SharedKernel (which is empty):

- `BaseEntity` — `Guid Id`, in-memory domain events list, equality by Id.
- `AuditableEntity` — extends `BaseEntity`; adds `CreatedUtc`, `UpdatedUtc`.
- `DomainEvent` — abstract `record` implementing MediatR `INotification`; carries `OccurredUtc`, optional `CorrelationId`/`CausationId`.
- `IAggregateRoot` — empty marker interface; `Traveler` and `Flight` implement it.
- `ValueObject` — equality by `GetEqualityComponents()`.

## Key Patterns

**Domain events:** Aggregates raise events in-memory via `Raise()`. `DomainEventDispatchInterceptor` publishes them via MediatR *after* `SaveChangesAsync` completes — so handlers always run post-commit and cannot roll back the DB write.

**MediatR pipeline:** `ValidationBehaviour<TRequest,TResponse>` runs before every handler. It collects all registered `IValidator<TRequest>` implementations, groups failures by property name, and throws `ValidationException`. Validators are auto-discovered from the Application assembly — no manual registration needed.

**Error handling:**
- `DomainException(message, statusCode=400, diagnosticDetail=null)` → `GlobalExceptionHandler` maps to `ProblemDetails` at the given status code.
- `ValidationException` → 400 `ValidationProblemDetails` with errors grouped by property name.
- Unhandled exceptions → 500.
- Every problem response carries a `traceId` extension — the request's correlation id (see `CorrelationIdMiddleware` below), falling back to `Activity.Current?.Id` then `HttpContext.TraceIdentifier` — for log correlation.
- `DomainException.DiagnosticDetail` is the operator-facing cause (e.g. the upstream provider's error code and message). It is rendered as ProblemDetails `Detail` **only outside Production**; Production callers get the title and `traceId` only. Never put credentials or request URLs in it — the value is client-visible in Development and Staging.

**Idempotent commands:** Handlers check for existing state before inserting (e.g., `RegisterTravelerCommand` queries by email first).

**Caching:** `ICacheService` abstraction. Redis is used when `ConnectionString:Redis` is configured; falls back to `IMemoryCache` otherwise. Injected directly into handlers — no decorator or pipeline pattern.

**Flight data provider:** FlightAware AeroAPI is the sole external provider for both flight status (`AeroApiFlightStatusProvider`) and flight search (`AeroApiFlightSearchProvider`). The `IFlightStatusProvider` / `IFlightSearchProvider` abstractions are kept so a fallback composite can be reintroduced for production. Both providers share one named `"AeroApi"` `HttpClient`, authenticated via the `x-apikey` header (never a URL query string, so there is nothing to sanitise out of telemetry), with Polly: `AeroApi:MaxRetryAttempts` retries (default 2), exponential backoff — except a 429 response, which is never auto-retried, since retrying a throttle response on a metered tier only makes it worse. All AeroAPI timestamps are UTC already (no timezone conversion needed on the way in). Both providers share `AeroApiResponse.ReadOrThrowAsync`, which reads the real HTTP status code AeroAPI signals failures with (no `error` body hidden under HTTP 200) and maps it to a `DomainException`: 401/403 (credential/plan problems) → 500, 429 (throttled) → 503 (with `Retry-After`), 400 (rejected parameters) → 400, anything else / unreachable / unparseable → 502. The upstream body — redacted of anything credential-shaped — is logged and carried in `DiagnosticDetail` (surfaced in the response outside Production); the client-facing `Message` never contains it. A successful search response with no matches returns an empty list, and a status response with no matching row returns `null` — both mean "no data", distinct from a provider failure.

**Flight search:** `AeroApiFlightSearchProvider` calls one endpoint, `GET /schedules/{date_start}/{date_end}`, covering a single rolling window from `AeroApi:MaxPastMonths` (default 3) months ago to `AeroApi:MaxFutureMonths` (default 12) months ahead — there is no live/future split to route between. `origin`, `destination`, `airline`, `flight_number` and `include_codeshares` all filter server-side, so there is no client-side route/flight-number filtering. AeroAPI paginates at roughly 15 rows per page; `AeroApi:MaxPages` (default 4) caps how many pages a single search fetches, bounding cost on a metered tier — a search that hits the cap logs a warning and returns what it has rather than fetching further pages. Raw schedule rows carry `actual_ident_iata`, which names the operating carrier's flight number on a codeshare row (null on the operating row itself); `IncludeCodeshares` just forwards to AeroAPI's own `include_codeshares` parameter, and the result stays one row per flight designator — `FlightSearchResult` deliberately carries no operating-carrier grouping.

**The local-day window shift.** `scheduled_out`/`scheduled_in` are UTC, but a search's `Date` is a local service date at the *origin* airport — a naive `[D, D+1)` UTC query can be wrong by nearly half a day for a far-east origin. `AeroApiFlightSearchProvider` resolves the origin's IANA zone via `AeroApiAirportTimezoneLookup` (`GET /airports/{id}`, cached 30 days) and shifts the query window to the exact UTC instants of local midnight and next-local-midnight, keeping it a strict 24 hours so page count is unaffected. When the origin (or its zone) is unknown — a flight-number-only search may carry no origin at all — the window widens to `[D−1, D+2)` UTC instead, and each row is then filtered by its own `origin_iata`'s zone once the response supplies it. If a row's own zone still cannot be resolved, the row is kept rather than dropped (the #275 principle: an unplaceable time is worse omitted than approximated), falling back to a UTC-calendar-date comparison as a last resort.

**`ServiceDate` is origin-local everywhere, status included.** Search reports the origin's local service date, `TrackFlightCommandHandler` stores it verbatim, and `SyncFlightStatusCommand` hands it back to `AeroApiFlightStatusProvider` — which therefore picks its matching `/flights/{ident}` row by converting `scheduled_out` into **that row's own `origin.timezone`** (already present in the payload, so no extra call) before comparing. Matching on the UTC calendar date instead selects the wrong day's operation for any airport far enough from UTC — AKL at UTC+13 departing 07:00 local is 18:00 Z the day before — and silently applies the next day's gate, terminal and status. A missing or unloadable zone falls back to the UTC comparison.

**`flight_statuses` is seeded reference data with permanent ids.** The seven codes (`SCH`, `DEP`, `ARR`, `DLY`, `CAN`, `DIV`, `UNK`) are seeded via `HasData` in `FlightStatusConfiguration`, so they live in the model snapshot and cannot drift per environment. **Their ids are permanent:** `flight_status_events.StatusId` is a foreign key, so renumbering one would silently repoint historical events at a different status. Add codes, never renumber them.

**An unrecognised status code degrades, it does not abort.** `SyncFlightStatusCommand` resolves the provider's code to a row id; an unknown code falls back to `UNK` and logs a warning naming the code, rather than throwing. Aborting would lose the traveler's status updates *and* discard a billable query already spent — by the time the code is resolved, `GetStatusAsync` has already run. The one loud failure is `UNK` itself being unresolvable: that means the reference table was never seeded, and every sync would otherwise burn a query per cycle and throw it away, so it throws.

**Search guard:** `AeroApiFlightSearchProvider` refuses any query that is not anchored on **both** ends of a route or on a flight number long enough to push down as `airline`+`flight_number` (≥ 2 chars). A single-airport query is ~700 rows in one call, and destination-only is worse than origin-only: with no origin there is no zone to anchor a local day on, so it runs over the widened 3-day window. The validator blocks these at the API edge; this guard is the backstop for every other caller.

**`links.next` is untrusted.** The `"AeroApi"` client attaches `x-apikey` to every request regardless of host, so a paging link is followed only if it resolves *underneath* `HttpClient.BaseAddress` — which rejects absolute, host-rooted and `../` links in one test. (Do not test "does it parse as absolute": `Uri.TryCreate("/schedules/…", UriKind.Absolute, …)` succeeds on Unix as a `file://` URI and would reject AeroAPI's own ordinary links.)

**Usage and spend come from the provider, never from a local meter.** `GET /admin/usage/aeroapi` proxies AeroAPI's own `GET /account/usage` via `AeroApiAccountUsageProvider` (same named client, same throttle, same `AeroApiResponse` error mapping), cached 10 minutes — FlightAware's own refresh cadence — under the resolved range. Do not reintroduce a local call-counting table (attempted and closed in PR #294): FlightAware bills per **page**, not per call, and bills **failed** calls too, so anything counted and priced locally is wrong in both directions and can never be reconciled against the invoice. `operation` arrives pre-normalised upstream, and `/account/usage` is itself billed at $0.00. The query defaults to the current UTC month to date with the end floored onto the 10-minute cache grid — an unrounded "now" would change the cache key on every request and spend a metered call each time — and its validator rejects a start older than AeroAPI's one-year history cap up front. `AeroApi:MonthlyBudgetUsd` and `AeroApiThrottleGate.NextSlotUtc` reach the Application handler through `IAeroApiBudgetOptions` / `IAeroApiThrottleObserver` (the `IFlightSearchHorizonOptions` translation pattern); both are attached fresh per request rather than cached alongside the upstream payload.

**CI results come from GitHub, through the API (#332).** `GET /admin/ci/runs` lists the CI workflow's runs and `GET /admin/ci/runs/{id}/tests` reads a run's `test-results.json` from the `test-results` artifact `ci.yml`'s Report step uploads, so the panel never holds a GitHub token. `GitHubCiRunProvider` gets two named clients and **only `"GitHub"` carries the token**: an artifact download answers 302 with a signed blob-storage URL, which is fetched with `"GitHubArtifactDownload"`, a client with no credentials. Neither client follows redirects itself, so whether the token reaches another host is decided by this code rather than by a handler's redirect rules; `GitHubDependencyInjectionTests` pins both, including against a registration that passes the token client as the download client. `GitHub:Token` is optional: without it the app still starts and both routes answer 503. The run list is cached 60 s. A report is cached for an hour **by artifact id, not run id**, because a re-run keeps its run id but uploads a new artifact. "No artifact yet" is never cached, so a run's report shows up as soon as it's uploaded. The downloaded archive (50 MB) and the decompressed report (20 MB) are both capped, since a zip entry's declared size can lie. The signed download URL is never logged. Upstream failures map like AeroAPI's: a rejected token or a 404 on the workflow is our configuration (500; GitHub answers 404 for a private repository the token can't see), a rate limit is 503 (403 counts only with `x-ratelimit-remaining: 0`, `Retry-After`, or a message saying so), anything else is 502.

**The typed admin drill-downs mask, and so do the older typed traveler endpoints (#321).** `GET /admin/travelers/{id}/detail` and `GET /admin/flights/{id}/detail` exist for what a generic browser cannot assemble — a traveler with their device tokens, tracked flights and memberships in one call, and a flight with its `FlightStatusEvent` history. All of `GET /admin/travelers`, `GET /admin/travelers/{id}` and the two drill-downs mask from `SensitiveProperties`, in the Application handler, exactly as the browser does — `GetAllTravelersQuery` and `GetAdminTravelerByIdQuery` share one `AdminTravelerResult.FromEntity` factory so the two typed routes cannot drift on whether `Email` is masked the way they did before #321 (both returned it in the clear, one route away from A4's masking and A5's audited reveal). `AdminResultMaskingCompletenessTests` (Application.Tests) is the backstop against this recurring: it fails the build the moment a new admin `*Result` record exposes a property name registered in `SensitiveProperties` without a reviewed, deliberate masking decision recorded alongside it.

**A capped collection fetches one row past the cap.** Both drill-downs bound their growing list — 50 status events, 50 tracked flights — with a real SQL `LIMIT` keeping the newest rows, and report a truncation flag. The flag is computed by asking for `Max + 1` and testing `> Max`, never by inferring from `Count == Max`: that inference reports a flight with *precisely* 50 events as truncated when it is complete, sending an operator to the generic browser for rows that are not there. The probe row is never returned. Only `traveler_flights` and `flight_status_events` are capped — memberships are schema-bounded by `UNIQUE(TravelerId, ProgramId)` and device tokens are tiny, so both stay whole. A4's browser pages all of these in full, so the drill-down is the recent view and the browser is the archive.

**Deleting a device token is not revoking a device.** It stops APNs pushes to that token; the client re-registers on next launch. The delete is audited for free by `AdminAuditInterceptor` because it goes through the tracked-entity path — which is exactly why it must stay there. Switching it to `ExecuteDeleteAsync` would bypass the `SaveChangesInterceptor` and silently stop auditing, and `FlightAssistantWebApplicationFactory` strips the interceptor entirely (#319), so an API-level test would still pass. Audit assertions for this belong in the Infrastructure suite, PostgreSQL-backed, where the interceptor is genuinely attached.

**Revealing a masked value is audited before the value is returned.** `POST /admin/data/{table}/{id}/reveal` hands back one full value of a column the browser masks — and the ordering is the feature: read the value, construct the `AdminAuditLog` row, `SaveChangesAsync`, **then** return. A failed save is a 500 with no value, because an unaudited reveal is the one outcome the endpoint must never produce. The row is written **explicitly**, not by `AdminAuditInterceptor`: a reveal is a read, nothing enters the `ChangeTracker`, so there is nothing for the interceptor to observe (it skips `AdminAuditLog` entries anyway, and its append-only guard rejects only `Modified`/`Deleted`, so an `Added` row passes). **The revealed value is never stored in that row** — `Before`/`After` stay null and `Summary` omits it; writing it would put the plaintext back into `admin_audit_log`, defeating masking-on-write and making the audit table the exfiltration path the reveal audit exists to detect. Only columns registered in `SensitiveProperties` are revealable; anything else is a 400, since a reveal returning a non-sensitive value is just an alternate read path around the browser. `POST` not `GET` (it has a side effect), `Cache-Control: no-store`, no audit row on a 404, and an `admin-reveal` rate limit partitioned by actor (`oid` → `sub` → IP, never IP alone) on that one route.

**`EntityId` comes from the loaded row's EF key metadata, never from the caller's string.** A caller-supplied `{C118FC0E-…}` would otherwise persist braced and uppercase while `AdminAuditInterceptor` writes the canonical lowercase form, and an auditor's `WHERE entity_id = '<guid>'` would silently miss those rows. Both writers reading the key from the same EF metadata is what stops them drifting; normalising strings by hand would need keeping in sync forever.

**The admin data browser is a whitelist, and the whitelist has a keeper.** `GET /admin/data/tables` and `GET /admin/data/{table}` read all 19 entity types through `BrowsableTables` (Application), an explicit registry of slug → CLR type → exposed columns. Explicit rather than reflection over `dbContext.Model`, so a new entity or column must be classified deliberately — but that only holds because `BrowsableTablesModelCompletenessTests` fails when the registry drifts from the model **in either direction**: a new `DbSet` left unclassified, or a new mapped property on an already-browsable entity left off both the exposed and excluded lists. Without those guards the registry would silently go stale, which is strictly worse than the reflection it replaced: reflection would at least have shown the new table. `NotBrowsable` carries a reason string so an exclusion is a decision, not an oversight. The tests live in `Infrastructure.Tests` because they need `ctx.Model` and `Application.Tests` must not gain an Infrastructure reference.

**`BrowsableTables` says what is exposed; `SensitiveProperties` says what is masked.** The browser projects every registered column, then replaces any value whose `(type, property)` is registered sensitive with `"<redacted>"` **before it leaves the API** — masking is in the Application handler, not the repository, which stays a generic paginated reader. Sensitivity is never duplicated onto `BrowsableTables`: one registry serves the audit interceptor's before/after snapshots, this projection, and A5's reveal, because two PII lists that both have to be right drift the way CLAUDE.md already describes for validator format rules — except that drift leaks PII. **A sensitive column is rejected in both `sort` and `filter` with a 400**: filtering it would make the browser an oracle for guessing a masked value one character at a time, and ordering leaks ordering.

**Column names are validated against the registry before reaching `EF.Property<object>()`, and matching is `Ordinal`.** Do not "improve" that to case-insensitive on its own — `SensitiveProperties.IsSensitive` is also Ordinal, so a case variant would pass the exposure check while failing the sensitivity check, making a sensitive column sortable. The safe version canonicalises the incoming name against the registry first and uses the canonical form for *both* checks.

**One correlation id, everywhere (#319).** `CorrelationIdMiddleware` accepts a valid `X-Correlation-Id` from the caller or mints one, and that single string reaches four places: the response header, every Serilog line (`LogContext`), ProblemDetails' `traceId`, and `admin_audit_log.TraceId`. Before this, three identifiers competed and the two that most needed correlation used the worst one — `Activity.Current?.Id`, which is **null for the entire request** unless `ApplicationInsights:ConnectionString` is set, because nothing registers an `ActivityListener` otherwise. So the audit log's correlation column was null on every row in every environment without App Insights, and ProblemDetails fell back to `HttpContext.TraceIdentifier`, which appears in no log line at all. A user quoting the id from a failed request now lands you on the logs *and* the audit row. It travels by `HttpContext.Items` rather than a scoped service because `GlobalExceptionHandler` is registered as a singleton and could not take a scoped dependency without a captive-dependency problem; Application and Infrastructure, which cannot see `HttpContext`, read it one hop later from `IAdminContext.CorrelationId`, populated by the `/admin` endpoint filter.

**Every admin write is audited in the same transaction as the write.** `AdminAuditInterceptor` reads the `ChangeTracker` on **`SavingChangesAsync`** — deliberately unlike `DomainEventDispatchInterceptor` next to it, which fires on `SavedChangesAsync`, *after* commit. An audit row that can roll back independently of the change it describes is worse than no audit row. Actor comes from a scoped `IAdminContext` (defined in **Application**, not API — Infrastructure has to resolve it and cannot reference API), populated by an endpoint filter on the `/admin` group; **no actor means no row**, so ordinary traveler traffic through the same `DbContext` is untouched. The **append-only guard sits above the actor gate**, so tampering with an audit row throws no matter who is saving. Actions derive from the tracker — `Verify` is a `Modified` whose changed properties are non-empty and entirely contained in the `IVerifiable` set, derived from the interface rather than a name list — with `Import` the single explicit override, because an upsert of 500 airports is otherwise indistinguishable from 500 manual edits and must be findable as one event. The rule is a subset, not an exact match (#355): `VerificationIssue` stays null→null on an ordinary `Verify()`/`Unverify()` call, so EF never marks it modified, and an exact-match rule would then miss the set on every such save and log it as an `Update` instead. Verifying *and* changing another property in the same save is still correctly an `Update`, since the modified set then contains a property outside `IVerifiable`.

**Sensitive values are masked on write and never stored.** `Traveler.Email`, `DeviceToken.Token` and `TravelerLoyaltyMembership.AccountNumber` record `"<redacted>"` in both `Before` and `After` — the fact of the change is captured, the value is not. Otherwise the audit log becomes a second, unprotected copy of exactly the PII A5 guards, reachable through a different endpoint, plus a GDPR-erasure liability. **The accepted cost: a redacted previous value is unrecoverable.** The classification lives in **one** `SensitiveProperties` registry in Application that A4's masking and A5's reveal also read; two copies of a PII list is the drift CLAUDE.md already names for validator format rules, except here the drift leaks PII. The placeholder string itself is the same kind of shared constant — `SensitiveProperties.RedactedPlaceholder` — read by this interceptor, `GetBrowsableDataQueryHandler` and `GetAdminTravelerDetailQueryHandler` alike, so a divergent literal in any one of them can never render a masked value that no longer looks masked. Look it up by `entry.Metadata.ClrType`, never `entry.Entity.GetType()` — a proxy type misses the registry, and a missed lookup is a silent leak.

**`AdminAuditLog.EntityId` is null for creates of store-generated-key entities.** Npgsql assigns identity keys during `SaveChanges` via `INSERT … RETURNING`, so at `SavingChanges` time the key does not exist, and recovering it would mean writing post-commit and forfeiting the whole transactional guarantee. It previously recorded EF's temporary sentinel (`-2147482647`), which reads as a real id and collides across every create of every type. Such a row is identified through `After`, which carries the created entity's full property set.

**`AdminAuditLog.TraceId` carries the request's correlation id, not `Activity.Current?.Id` (#319).** Before this fix there were three competing identifiers — `CorrelationIdMiddleware`'s id (always present: response header + every Serilog line), `Activity.Current?.Id` (only present with App Insights configured), and `HttpContext.TraceIdentifier` (always present, but in no log line) — and both `TraceId` and ProblemDetails' `traceId` used the one least likely to exist, making the audit log's own correlation column uncorrelated with anything an operator could actually search. `CorrelationIdMiddleware` now stashes its id on `HttpContext.Items` (`CorrelationIdMiddleware.ItemsKey`); the `/admin` endpoint filter (`Program.cs`) copies it onto `IAdminContext.CorrelationId` — Infrastructure and Application cannot see `HttpContext`, so this is the same routing `ActorId` already uses — and both audit writers (`AdminAuditInterceptor`, `RevealValueCommandHandler`) resolve `TraceId` as `_adminContext.CorrelationId ?? Activity.Current?.Id`, correlation id first. `GlobalExceptionHandler` reads the same `HttpContext.Items` value for ProblemDetails' `traceId`. **This changed an existing response field's value**: `traceId` now carries the 32-hex correlation id instead of a W3C trace id or ASP.NET connection id — intended, since a `traceId` absent from every log line was never useful, but visible to any client that was parsing the old format.

**The admin drill-downs (#322) are a new route each, not an extension of an existing one.** `GET /admin/travelers/{id}/detail` returns the traveler with its device tokens, tracked flights (joined server-side with their `Flight` row, including both airport ids so a caller can draw the route without a second call) and loyalty memberships in one call, masking `Traveler.Email`, `DeviceToken.Token` and `TravelerLoyaltyMembership.AccountNumber` — all three registered in `SensitiveProperties` — the same way `GetBrowsableDataQueryHandler` does: in the Application handler (`GetAdminTravelerDetailQueryHandler`), never the repository. It does not extend the existing `GET /admin/travelers/{id}`, whose `AdminTravelerDto` is the narrower row shape (no device tokens, tracked flights or memberships — both mask `Email` the same way since #321): bolting relationship data onto that route would also have to silently change its response shape for anyone already calling it, and a single route whose shape depends on nothing visible in the request is worse than two routes with two clear, separate contracts. `GetAdminTravelerDetailQueryHandler` calls three repositories — `IAdminTravelerRepository`, `IFlightRepository`, `ILoyaltyRepository` — each resolving its relationship server-side (an `Include`, or a LINQ `Join`) in one query apiece, a fixed count that does not grow with how many tokens/flights/memberships the traveler has; the read side of each is `AsNoTracking`. Memberships (`ORDER BY ProgramId`, in `LoyaltyRepository`) and device tokens (sorted by `LastSeenUtc` in the handler itself, since they load through the traveler's own `Include` rather than a separate `IQueryable`) both carry a deterministic order — PostgreSQL gives none for free, and an admin panel re-rendering the same traveler in a different order between two identical calls is churn with no cause. Tracked flights is the one relationship of the three actually capped: `traveler_flights` has no retention/purge path and grows monotonically with usage, unlike memberships (schema-bounded by `UNIQUE(TravelerId, ProgramId)`) or device tokens (small in practice). `IFlightRepository.GetRecentTravelerFlightsAsync` caps it at `GetAdminTravelerDetailQueryHandler.MaxTrackedFlights` (50) via a server-side `LIMIT`, newest-serviced first, and `AdminTravelerDetailResult.TrackedFlightsTruncated` tells a caller when that cap actually cut rows off — `GET /admin/data/traveler-flights` (A4) already pages the full relationship, so the truncation flag is what points a caller from the "recent" drill-down view to that archive.

**`GET /admin/flights/{id}/detail` derives "current status" from the newest `FlightStatusEvent`, and caps the history it returns.** There is no separate current-status column on `Flight` — `CurrentStatus` is simply `StatusHistory[0]`, since `IFlightRepository.GetRecentFlightStatusEventsAsync` already returns events newest-first. The history is capped at `GetAdminFlightDetailQueryHandler.MaxStatusHistory` (50) via a server-side `LIMIT`, not the unbounded `GetFlightStatusEventsAsync` the traveler-facing status endpoint already uses — a flight tracked for weeks and polled every couple of minutes accumulates rows without bound, and this "one call" detail view must not load all of them just to show the recent ones. `AdminFlightDetailResult.StatusHistoryTruncated` (fetch `MaxStatusHistory + 1`, test `> MaxStatusHistory` — see "A capped collection fetches one row past the cap") is what lets a caller tell "exactly 50 events, capped" apart from "exactly 50 events, full stop" — the cap alone is otherwise documented only in Swagger/XML, invisible in the JSON itself — and points to `GET /admin/data/flight-status-events` (A4) for the rest. Each row also carries the provider's raw status text — e.g. AeroAPI's `"En Route / On Time"` — extracted from `FlightStatusEvent.RawPayloadJson` (the whole raw AeroAPI row `AeroApiFlightStatusProvider` already stores) rather than a column of its own; null — "where recorded" — for a row with no payload at all, such as a manually-created event. Because `FlightStatus` has no public constructor (only EF's own materialiser ever populates its navigation), the per-event mapping can only be proved against a real `Include`, not a mock — see `AdminDrilldownRepositoryTests` (Infrastructure.Tests, PostgreSQL-backed), which is also where this endpoint's "one query, not N+1" guarantee is proved by actually counting SQL statements via a `DbCommandInterceptor`, since InMemory never issues a `DbCommand` at all.

**The device-token delete's audit-row guarantee is tied to the handler itself, not just to the interceptor.** `AdminAuditInterceptorPostgresTests.Handle_DeviceTokenDeletedThroughTheRealHandler_WritesADeleteAuditRow` constructs the real `DeleteDeviceTokenCommandHandler` against a real, audited `AdminTravelerRepository` — unlike its neighbour in the same file, which proves the interceptor audits a tracked `DeviceToken` removal by hand-rolling the same two lines the handler happens to contain today. That distinction is not cosmetic: measured by temporarily deleting the handler's `traveler.RemoveDeviceToken(...)` call, the hand-rolled test still passed 6/6 while this one failed — a future change that swapped the delete to `ExecuteDeleteAsync` (works on PostgreSQL, throws on InMemory — #295) would bypass the change tracker, and this interceptor, exactly the same way, silently losing the audit trail while the API-level test and every other existing test kept passing.

**`DELETE /admin/travelers/{travelerId}/device-tokens/{tokenId}` is audited for free, and is explicit that it is not a device revocation** (it only stops APNs pushes to that token; the client re-registers on next launch). `DeviceTokenConfiguration`'s FK to `Traveler` is `OnDelete(Cascade)`, so removing a token from a loaded, tracked `Traveler.DeviceTokens` collection marks that `DeviceToken` entry `Deleted` in the change tracker — `AdminAuditInterceptor` picks it up on its own; `DeleteDeviceTokenCommandHandler` never builds an audit row itself. Removing a token also touches the parent `Traveler` (`RemoveDeviceToken` calls `SetUpdated()`), so one delete actually produces *two* audit rows — a `Delete` for the `DeviceToken` and an `Update` for the `Traveler` — both correct, since both entities really did change in that `SaveChanges` call. An unknown traveler or an unknown token both 404 before `SaveChangesAsync` is ever called, so neither produces a row. This is deliberately a new command (`Commands.Admin.Travelers.DeleteDeviceTokenCommand`), not a reuse of the traveler-facing `Commands.Travelers.RemoveDeviceTokenCommand`: that handler treats an unknown token as a silent no-op and always saves, which would give every unknown-token call here a 204 and (harmlessly, since nothing changed) no audit row — a "success" response that is the opposite of the required 404.

**Date query parameters on admin endpoints bind `DateTimeOffset?`, never `DateTime?`.** A bare `?fromUtc=2026-09-01` with no `Z` or offset binds as `DateTimeKind.Unspecified`, which Npgsql refuses against a `timestamptz` column — an unhandled `ArgumentException` and a 500. **This has now cost two bugs** (`/admin/usage/aeroapi` and `/admin/audit`), both invisible to the API test suite because it runs on the InMemory provider, which accepts an Unspecified `Kind` happily. Any endpoint taking a date needs either a `DateTimeOffset?` parameter or a PostgreSQL-backed test — the #295 harness exists for exactly this class of divergence.

**`/admin/health` is the operator view; `/health/ready` is a probe.** `GET /admin/health` runs `HealthCheckService.CheckHealthAsync()` with **no predicate**, so the `external` checks (`aeroapi`, `apns`) that `/health/ready` deliberately excludes are included — App Service restarts the app on a 503, so a flaky FlightAware host must never be able to cause one, which is exactly what makes `/health/ready` useless to an operator. It returns **200 even when the overall status is `Unhealthy`**: a report, not a probe, and a non-2xx makes the panel's error handling swallow the body that explains the failure. It costs no metered query — `AeroApiHealthCheck` builds a *bare* `IHttpClientFactory.CreateClient()` and sends a HEAD, so it carries no `x-apikey` and passes through no `AeroApiThrottlingHandler`; do not "improve" it into a real API call. Uniquely among the admin endpoints it is mapped **without MediatR**, because every input is a hosting artifact (`HealthCheckService`, `IHostEnvironment`, `IConfiguration`, the entry assembly, the `DbContext`'s migration lists) and Application-side translation interfaces for them would buy nothing testable; the shaping lives in `AdminHealthReportBuilder` instead. Exception detail, and `flightSync.lastError`, follow the `DiagnosticDetail` convention and render outside Production only; `redisConfigured`/`appInsightsConfigured` are booleans precisely so no connection string can escape through a diagnostics endpoint.

**"Cannot tell" is not "nothing pending".** `AdminHealthMigrationsDto.Available` is `false` both on a non-relational provider *and* when the migration-history read throws. `Database.IsRelational()` answers a **provider** question — it is `true` for Npgsql whether or not Postgres is reachable — but `GetApplied`/`GetPendingMigrationsAsync` need a live connection, so a database outage threw a raw `NpgsqlException` that took the whole report down with it, returning 500 at exactly the moment an operator needs the page, while the `database` check beside it degraded gracefully via `CanConnectAsync`. Both failure modes now report `Available: false` with a gated reason rather than an empty `Pending` list, which would be a different and much stronger claim.

**`FlightStatusSyncBackgroundService` publishes a heartbeat.** It swallows per-flight exceptions and retries on batch failure, so a service failing every cycle was indistinguishable from a healthy one from outside. `FlightSyncHeartbeat` (API layer — writer and reader both live there, so no cross-layer interface) publishes an **immutable `FlightSyncSnapshot` by atomic reference write**; that, not the lock, is what makes a concurrent reader safe. The lock serialises the read-modify-write inside the `Mark*` methods so a second writer, if one is ever added, cannot lose an update. `FlightsProcessed` counts flights **attempted** and `FlightsFailed` the subset that threw — a batch completing with failures is still outcome `Success`, because the *batch* ran. When `FlightSync:Enabled` is false the heartbeat stays at `NeverRun` with null timestamps, which must read as *disabled*, not *broken*.

**Each tracked flight is synced on its own schedule (#356).** `FlightSyncPlanner` (Application) gives a flight a mode from its times, status and tracking, first match wins: none (no traveler tracks it); `Stopped` (`FlightSync:StopAfterArrival` after its actual arrival or `CancelledAtUtc`, or `StopWithoutArrivalAfter` after an arrival that is never reported); `Fast` (from `FastWindowBeforeDeparture` before the *estimated*, else scheduled, departure; every `NearDepartureInterval`); `Live` (from `AeroApi:StatusWindowFutureDays` before the *scheduled* departure, the first moment `/flights/{ident}` can answer, #343; every `Interval`); `Schedule` (further out). The next sync is capped at the moment the mode would change, so a stored mode is at most one loop stale. `FlightStatusSyncBackgroundService` wakes every `LoopInterval` and sends `SyncFlightStatusCommand(null, id, SyncTrigger.Scheduled)` only for tracked flights with `NextSyncDueUtc <= now` or no mode at all (never planned: tracked by an older build between the migration and the app deploy, or a track racing the last untrack), unplanned first, then oldest due, **each in its own DI scope** so a flight that fails part-way can't be saved by the next one's `SaveChanges`. A loop sync of a flight that's no longer due (a manual sync ran after the loop listed it) makes no call and saves nothing. The loop never calls AeroAPI for a Stopped flight; an admin or traveler sync still does, because a person asked. `ActualArrivalUtc` is AeroAPI's gate arrival (`actual_in`), falling back to runway arrival (`actual_on`), which is often all AeroAPI reports; without the fallback a landed flight stops only by `StopWithoutArrivalAfter`. Schedule-mode flights make no call yet (the `/schedules` check is step 2 of #349) and are next due when Live starts. `LastSyncedUtc` records every call that returned, empty or duplicate included; a loop call that throws keeps the flight's mode and moves its next sync one interval on without marking it synced, because a failed call can still be billed and retrying every loop would cost a call a minute; a person's call that throws saves nothing. Tracking an unplanned flight makes it due now; the last untrack clears its mode but keeps `LastSyncedUtc`. Deleting a traveler doesn't clear plans; the loop ignores untracked flights, so that costs no calls.

**Shared outbound throttle:** `AeroApiThrottleGate`, a process-wide singleton applied via `AeroApiThrottlingHandler` to every AeroAPI `HttpClient`, spaces every outbound call — search or status — by `AeroApi:MinRequestInterval` (default 12 s, ≈5 requests/minute) to stay inside the personal tier's rate limit, regardless of which caller sent it. A caller reserves the next slot under a lock and waits it out without holding the lock; a reservation whose wait is cancelled is **released**, so an abandoned attempt never pushes the queue further out for everyone behind it.

**The throttle sits *inside* the resilience handler** (registered second, so it is closer to the transport) — deliberately, so every retry attempt is throttled too. The consequence is that a throttled wait of up to a whole `MinRequestInterval` elapses *within* the per-attempt timeout, so **every resilience timeout is derived from `MinRequestInterval`, never left at a library default or hardcoded** (`AeroApiOptions.AttemptTimeout` = interval + `TimeoutSeconds`; `TotalRequestTimeout` covers every attempt plus backoff; `CircuitBreakerSamplingDuration` ≥ 2× attempt; `HttpClient.Timeout` is a looser backstop outside all of it). With the library's 10 s default against a 12 s interval, every second call in an interval window was killed before it reached the transport, retried twice, and then failed the 30 s total timeout — surfacing as a 502 after a 30-second hang, and breaking every multi-page search from page 2 on. `AeroApiClientPipelineTests` sends real requests through the composed named client (on a `FakeTimeProvider`) because no test that only *resolves* DI objects, or that builds a bare `HttpClient`, can see this.

**Paging:** Input `PagedRequest(Page=1, PageSize=50)`, output `PagedResult<T>(Items, Total, Page, PageSize)`. Validated by `PagedRequestValidator` (Page ≥ 1, PageSize 1–200, and `(Page - 1) * PageSize` must fit in an `int` — the overflow boundary, not an arbitrary cap, #316). Repositories page through the one `PagedQueryableExtensions.Page` helper, which clamps offset to `[0, int.MaxValue]` as a backstop for callers that bypass the validator; never write `Skip((page - 1) * pageSize)` inline. Reuse `PagedRequestValidator` in query validators via `.SetValidator(new PagedRequestValidator())`.

**RefDataRepository:** Consolidates all reference data reads (airports, airlines, countries, alliances) in a single repository intentionally — see the file for rationale; planned to split later.

**`spec/openapi.json` is generated, not hand-authored.** It comes from booting the API host and walking its own route/DTO metadata via Swashbuckle's CLI (`dotnet swagger tofile`, pinned in `.config/dotnet-tools.json`) — regenerate it with `scripts/generate-openapi.sh` from the repo root (the tool manifest is repo-local, so `dotnet swagger` only resolves there; run elsewhere and the dotnet CLI's answer — "You misspelled a built-in dotnet command" — points nowhere near the real cause, which is why the script checks first and says so plainly). The host needs *some* configuration to start — `AeroApiOptions.ApiKey` is `[Required]` and validated on start — so the script boots it on dummy values; the export makes no outbound call and the spec itself carries no configuration values, so a dummy is enough. That block is defined exactly once, inside the script, and both `ci.yml` and `development_flight-assistant-dev-api.yml`'s "Export OpenAPI spec" step call it rather than each keeping a copy. Generation is deterministic — `SwaggerDoc`'s `Version` is a fixed `"v1"`, not a build stamp — which is what lets `ci.yml` regenerate the spec on every PR and fail the build, diff and regenerate command included in the log, if it doesn't match the committed file byte-for-byte; that same check also asserts the regenerated spec contains none of the dummy credential values, since a public-shaped document is exactly where a future leaked example or default would surface. Never hand-edit `spec/openapi.json` — CI will only hand you back a diff, not a fix.

## Conventions

**File layout in Application:**
- Commands: `Application/Commands/{Domain}/{CommandName}.cs` — command record, validator, and handler all in one file.
- Queries: `Application/Queries/{Domain}/{QueryName}.cs` — same pattern.
- Validators: named `{CommandName}Validator`, defined in the same file as the command.
- A format rule shared by more than one validator lives in **one** constant, not two copies of a regex. `Application/Validators/FlightNumberFormat.cs` holds the IATA flight designator pattern used by both `SearchFlightsQueryValidator` and `TrackFlightCommandValidator`, plus a `Description` the Swagger text is rendered from — they had drifted in *both* directions (search accepted an all-digit prefix track refused; track accepted a trailing letter search refused), which is exactly the "search returns a row `POST /flights` rejects" defect the search reshape exists to remove.

**Repository contract:** `SaveChangesAsync()` is called explicitly inside handlers. There is no implicit unit-of-work auto-save.

**External service options:** All external service config uses the Options pattern — `AddOptions<T>().BindConfiguration(section).ValidateOnStart()`.

**Database:**
- Table names: `snake_case` (e.g., `travelers`, `device_tokens`, `traveler_flights`).
- All timestamps: UTC only, suffixed `Utc` (e.g., `CreatedUtc`, `ScheduledDepartureUtc`), stored as `timestamptz`.

**Naming:**
- Commands return a value or `Unit`; queries return data — both are `IRequest<T>`.
- Result/DTO types: `{Name}Result` or `{Name}Dto`.
- Endpoint tag group names match the bounded context (e.g., `"Travelers"`, `"Flights"`).

## Authentication

- JWT Bearer via Azure AD B2C / Entra External ID.
- Traveler identity = `oid` claim (falls back to `sub`), parsed as `Guid`. Use `ClaimsPrincipalExtensions.GetTravelerId()`.
- Scope enforcement: `http.VerifyUserHasAnyAcceptedScope("access_as_user")` at the start of each user-facing handler.
- Admin endpoints use the `"AdminOnly"` authorization policy: authenticated + role claim `"admin"`.
- `TravelerContextMiddleware` enriches Serilog's `LogContext` with TravelerId for every authenticated request.
