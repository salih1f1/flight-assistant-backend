## Architecture

ASP.NET Core Web API using **Clean Architecture + CQRS** (MediatR) with **Domain-Driven Design**.

**Layers:**
- `FlightAssistant.Domain` — Aggregates, entities, domain events, value objects, exceptions. Private constructors everywhere; use factory methods.
- `FlightAssistant.Application` — MediatR command/query handlers + FluentValidation validators. All use cases live here.
- `FlightAssistant.Infrastructure` — EF Core + PostgreSQL, Redis, HTTP clients for external APIs, APNs.
- `FlightAssistant.API` — Minimal API endpoints, middleware, DI wiring in `Program.cs`, hosted services.
- `FlightAssistant.Contracts` — Request/response DTOs. No dependencies on other layers.
- `FlightAssistant.SharedKernel` — Currently empty; base classes live in `Domain/Common/` instead.

**Bounded contexts:** Travelers, Flights, Loyalty, Lounges, Configuration (reference data).

## Domain Base Classes

All live in `FlightAssistant.Domain/Common/`, **not** SharedKernel (which is empty):

- `BaseEntity` — `Guid Id`, in-memory domain events list, equality by Id.
- `AuditableEntity` — extends `BaseEntity`; adds `CreatedUtc`, `UpdatedUtc`.
- `DomainEvent` — abstract `record` implementing MediatR `INotification`; carries `OccurredUtc`, optional `CorrelationId`/`CausationId`.
- `IAggregateRoot` — empty marker interface; `Traveler` and `Flight` implement it.
- `ValueObject` — equality by `GetEqualityComponents()`.

## Key Patterns

**Domain events:** Aggregates raise events in-memory via `Raise()`. `DomainEventDispatchInterceptor` publishes them via MediatR *after* `SaveChangesAsync` completes — so handlers always run post-commit and cannot roll back the DB write.

**MediatR pipeline:** `ValidationBehaviour<TRequest,TResponse>` runs before every handler. It collects all registered `IValidator<TRequest>` implementations, groups failures by property name, and throws `ValidationException`. Validators are auto-discovered from the Application assembly — no manual registration needed.

**Error handling:**
- `DomainException(message, statusCode=400, diagnosticDetail=null)` → `GlobalExceptionHandler` maps to `ProblemDetails` at the given status code.
- `ValidationException` → 400 `ValidationProblemDetails` with errors grouped by property name.
- Unhandled exceptions → 500.
- Every problem response carries a `traceId` extension — the request's correlation id (see `CorrelationIdMiddleware` below), falling back to `Activity.Current?.Id` then `HttpContext.TraceIdentifier` — for log correlation. That holds for problems `GlobalExceptionHandler` writes; framework-produced problems (`UseStatusCodePages`) carry `HttpContext.TraceIdentifier` instead, so #319's promise does not reach them — tracked in #413.
- `DomainException.DiagnosticDetail` is the operator-facing cause (e.g. the upstream provider's error code and message). It is rendered as ProblemDetails `Detail` **only outside Production**; Production callers get the title and `traceId` only. Never put credentials or request URLs in it — the value is client-visible in Development and Staging.
- Every response that carries a **problem document** uses **`application/problem+json`** (RFC 9457), whichever layer produced it — `GlobalExceptionHandler`, the validation pipeline, ASP.NET's model binding, or an endpoint's own `Results.NotFound()`. Those framework bodies come from `UseStatusCodePages()` (`Program.cs`) paired with `AddProblemDetails()`: the originating code (model binding, `Results.NotFound()`, the auth policies) sets a status and no body, and that middleware fills one in. Deleting either as apparently unused blanks the body of every 400/401/403/404/405 in the API. Responses that carry **no** problem document are outside this, and there are three kinds: the rate limiter's 429, which `OnRejected` (`Program.cs`) writes as a bare text body — no content type at all — beside its `Retry-After` header; the scope-failure 403 from `VerifyUserHasAnyAcceptedScope`, which commits a 403 with no content type before throwing (#413); and **any** framework-produced error whose request does not accept JSON — `UseStatusCodePages` then falls back to a `text/plain` "Status Code: N; …" body, so a browser navigating to an API URL gets text, not a problem document. `GlobalExceptionHandler`, by contrast, ignores `Accept` and always writes the problem document. Before #415 the handler passed `contentType: null` to `WriteAsJsonAsync` and sent `application/json`, so handler-produced problems contradicted the 122 spec entries declaring otherwise while the framework's own matched them — two 404s one route apart disagreed. The handler deliberately does **not** route through `IProblemDetailsService`, for two measured reasons, neither of which is `Title` (which that service leaves alone — it applies `Title ??=`): it overwrites the `traceId` extension with `Activity.Current?.Id ?? HttpContext.TraceIdentifier`, regressing #319's correlation id in the one place a caller can read it, and it declines to write at all when the request's `Accept` excludes JSON, which would turn a handler problem into a bodyless response. It would also fill `Type`, changing every problem body.
- **What a route declares, and what it does not.** `.Produces*` lists every status **only this operation can produce** — thrown by its handler, raised by the validation pipeline, or returned by the endpoint itself. It deliberately does **not** list two different things. First, the genuinely ambient statuses — 401, and the 403 for lacking authorisation, which comes from `VerifyUserHasAnyAcceptedScope` on traveler routes and from the `AdminOnly` role policy on the whole `/admin` group — which can arise on *every* authenticated route, so declaring them per-route would add noise to every operation without telling a client anything route-specific. Second, **429, which is not ambient**: only the few routes carrying `RequireRateLimiting` can return it. It stays undeclared by a separate and deliberate convention — no route in this repository declares it, and the limiter's own `Retry-After` header is self-describing — and it is documented in description prose instead. Do not defend leaving 429 undeclared by calling it ambient: that reasoning is false, and it would licence leaving a genuinely route-specific status undeclared. A declared status that no handler can produce is worse than an undeclared one: a generated client branches on a response it will never receive (#405). The four per-flight routes differ in the status they answer with, not in what they reveal: every one of them keys off the same `GetTravelerFlightAsync` lookup, so a flight the traveler does not track is indistinguishable from one that does not exist, and none of them discloses whether an id is real. `GET /flights/{id}/status` and `POST /flights/{id}/sync` answer 403; `PATCH /flights/{id}/notify` answers 404, which reads as being about the traveler's tracking list rather than the flight but conceals exactly as much; and `DELETE /flights/{id}` is idempotent, answering 204 either way. Do not infer disclosure from the status code — the 404 and the 403 here hide the same thing. **Never declare both `.ProducesValidationProblem()` and `.ProducesProblem(400)` on one route.** OpenAPI allows one entry per status and the later declaration wins, so the pair renders as `400(ProblemDetails)` and silently loses the `errors` dictionary — that is what `AdminUsageEndpoints` and the eight import routes currently produce, despite a comment there intending the opposite. Where a route can return both a validation 400 and a plain `DomainException(…, 400)` — verified for the verification `accept-source` and `retry` routes — declaring only `.ProducesValidationProblem()` is deliberate: `HttpValidationProblemDetails` extends `ProblemDetails`, so it is the better of two imperfect options. The real fix would be a `oneOf`, which Swashbuckle will not emit from these attributes. Three sibling verification routes also throw a `DomainException(…, 400)`, but it duplicates their own validator's check and `ValidationBehaviour` runs first, so that branch is unreachable — they have one 400 shape, not two.

**Idempotent commands:** Handlers check for existing state before inserting (e.g., `RegisterTravelerCommand` queries by email first).

**Caching:** `ICacheService` abstraction. Redis is used when `ConnectionString:Redis` is configured; falls back to `IMemoryCache` otherwise. Injected directly into handlers — no decorator or pipeline pattern.

**Flight data provider:** FlightAware AeroAPI is the sole external provider for both flight status (`AeroApiFlightStatusProvider`) and flight search (`AeroApiFlightSearchProvider`). The `IFlightStatusProvider` / `IFlightSearchProvider` abstractions are kept so a fallback composite can be reintroduced for production. Both providers share one named `"AeroApi"` `HttpClient`, authenticated via the `x-apikey` header (never a URL query string, so there is nothing to sanitise out of telemetry), with Polly: `AeroApi:MaxRetryAttempts` retries (default 2), exponential backoff — except a 429 response, which is never auto-retried, since retrying a throttle response on a metered tier only makes it worse. A scheduled status poll isn't retried either (#375): `SyncFlightStatusCommandHandler` passes `StatusCallKind.ScheduledPoll` for a `Scheduled` sync, `AeroApiFlightStatusProvider` marks that request with `AeroApiRetry.Skip`, and the retry predicate skips marked requests, because AeroAPI bills failed calls and the loop's next due sync is the retry. Searches, timezone lookups, the usage report and syncs a person triggers keep their retries. All AeroAPI timestamps are UTC already (no timezone conversion needed on the way in). Both providers share `AeroApiResponse.ReadOrThrowAsync`, which reads the real HTTP status code AeroAPI signals failures with (no `error` body hidden under HTTP 200) and maps it to a `DomainException`: 401/403 (credential/plan problems) → 500, 429 (throttled) → 503 (with `Retry-After`), 400 (rejected parameters) → 400, anything else / unreachable / unparseable → 502. The upstream body — redacted of anything credential-shaped — is logged and carried in `DiagnosticDetail` (surfaced in the response outside Production); the client-facing `Message` never contains it. A successful search response with no matches returns an empty list, and a status response with no matching row returns `null` — both mean "no data", distinct from a provider failure.

**Flight search:** `AeroApiFlightSearchProvider` calls one endpoint, `GET /schedules/{date_start}/{date_end}`, covering a single rolling window from `AeroApi:MaxPastMonths` (default 3) months ago to `AeroApi:MaxFutureMonths` (default 12) months ahead — there is no live/future split to route between. `origin`, `destination`, `airline`, `flight_number` and `include_codeshares` all filter server-side, so there is no client-side route/flight-number filtering. AeroAPI paginates at roughly 15 rows per page; `AeroApi:MaxPages` (default 4) caps how many pages a single search fetches, bounding cost on a metered tier — a search that hits the cap logs a warning and returns what it has rather than fetching further pages. Raw schedule rows carry `actual_ident_iata`, which names the operating carrier's flight number on a codeshare row (null on the operating row itself); `IncludeCodeshares` just forwards to AeroAPI's own `include_codeshares` parameter, and the result stays one row per flight designator — `FlightSearchResult` deliberately carries no operating-carrier grouping.

**The local-day window shift.** `scheduled_out`/`scheduled_in` are UTC, but a search's `Date` is a local service date at the *origin* airport — a naive `[D, D+1)` UTC query can be wrong by nearly half a day for a far-east origin. `AeroApiFlightSearchProvider` resolves the origin's IANA zone via `AeroApiAirportTimezoneLookup` (`GET /airports/{id}`; a success is cached for 365 days, an airport AeroAPI doesn't know for 1 hour, and a transient failure not at all, #373) and shifts the query window to the exact UTC instants of local midnight and next-local-midnight, keeping it a strict 24 hours so page count is unaffected. When the origin (or its zone) is unknown — a flight-number-only search may carry no origin at all — the window widens to `[D−1, D+2)` UTC instead, and each row is then filtered by its own `origin_iata`'s zone once the response supplies it. Each distinct origin is looked up once per search, not once per row, so an origin whose lookup fails can't cost a billed call per row (#373). A transient failure isn't cached because a cached miss would send that origin's searches to the UTC-date fallback, which gives wrong-day rows for far-offset airports, and the search cache would keep them. If a row's own zone still cannot be resolved, the row is kept rather than dropped (the #275 principle: an unplaceable time is worse omitted than approximated), falling back to a UTC-calendar-date comparison as a last resort.

**`ServiceDate` is origin-local everywhere, status included.** Search reports the origin's local service date, `TrackFlightCommandHandler` stores it verbatim, and `SyncFlightStatusCommand` hands it back to `AeroApiFlightStatusProvider` — which therefore picks its matching `/flights/{ident}` row by converting `scheduled_out` into **that row's own `origin.timezone`** (already present in the payload, so no extra call) before comparing. Matching on the UTC calendar date instead selects the wrong day's operation for any airport far enough from UTC — AKL at UTC+13 departing 07:00 local is 18:00 Z the day before — and silently applies the next day's gate, terminal and status. A missing or unloadable zone falls back to the UTC comparison.

**`flight_statuses` is seeded reference data with permanent ids.** The seven codes (`SCH`, `DEP`, `ARR`, `DLY`, `CAN`, `DIV`, `UNK`) are seeded via `HasData` in `FlightStatusConfiguration`, so they live in the model snapshot and cannot drift per environment. **Their ids are permanent:** `flight_status_events.StatusId` is a foreign key, so renumbering one would silently repoint historical events at a different status. Add codes, never renumber them.

**An unrecognised status code degrades, it does not abort.** `SyncFlightStatusCommand` resolves the provider's code to a row id; an unknown code falls back to `UNK` and logs a warning naming the code, rather than throwing. Aborting would lose the traveler's status updates *and* discard a billable query already spent — by the time the code is resolved, `GetStatusAsync` has already run. The one loud failure is `UNK` itself being unresolvable: that means the reference table was never seeded, and every sync would otherwise burn a query per cycle and throw it away, so it throws.

**A status the flight already has still updates it (#351).** `SyncFlightStatusCommandHandler` records a new status as a `FlightStatusEvent` and calls `Flight.ApplyStatusUpdate`, which raises `FlightStatusChanged`; the push handler acts on its `ShouldNotify` (#352). When the status hash (`FlightStatusEvent.ComputeDedupHash`: flight, status, effective time, source, provider id) is already stored, the response is no longer dropped. `Flight.ApplyProviderTimes` takes its estimated and actual times, the scheduled departure and arrival (#399 — kept, not overwritten, when the provider omits one, exactly like the actual times, since an airline retime must reach the planner's Live window, which reads `ScheduledDepartureUtc` directly, and the tracking cap's stop rule, which reads `EstimatedArrivalUtc ?? ScheduledArrivalUtc`), and aircraft type without raising an event, and those times feed the planner (the Fast window, the Stopped rule and the #380 active-flight count). An actual departure or arrival, once reported, is kept when a later response omits it — on both paths — because clearing an actual arrival would send a landed flight back to the no-arrival Stopped rule and up to a day of Fast polls the budget guard doesn't hold back. A gate, terminal or baggage claim that differs from the flight's latest event (the most recently recorded), for the same status as that event, is recorded with `FlightStatusEvent.CreateDetailChange`. A response whose status matches an older event but not the latest records nothing, as before; a status that flips back, or an out-of-order response, needs its own handling, which Phase 2's alerts will have to decide. Neither path sends a push, and a detail the provider stops reporting keeps its last known value. A detail change can't reuse the status hash, because `(FlightId, Source, DedupHash)` is unique, so `ComputeDetailChangeHash` hashes the status identity plus the id of the event it follows and the details, which stays unique even when a gate changes back. **Never change `ComputeDedupHash`'s formula:** every stored hash would stop matching, and each tracked flight would record, and push, its latest status again (`ComputeDedupHash_FormulaIsUnchanged` pins it). Event lists (`GET /flights/{id}/status`, the admin flight detail and its `CurrentStatus`) order by id, most recently recorded first, so their first row is the event a sync compares against. Effective time can move backwards when an estimate returns to an earlier value, so it doesn't say which event is current.

**A push goes out when a status travelers hear changes, or a delay grows (#352).** `AeroApiFlightStatusProvider` decides a delay from the times before departure. With both `scheduled_out` and `estimated_out`, a scheduled or delayed flight is `DLY` when the estimate is at least `Flight.DelayThreshold` (15 min) late and `SCH` otherwise, whatever the prose says: AeroAPI writes a delay both as a qualifier (`"Scheduled / Delayed"`) and as a leading `"Delayed"`. Without both times, a `"Delayed"` segment still means `DLY`. `"Taxiing"` maps to `DEP`. `SyncFlightStatusCommandHandler` passes `statusChanged` (the new status id against the flight's latest event, #351) and AeroAPI's current `scheduled_out` to `Flight.ApplyStatusUpdate`, which sets `FlightStatusChanged.ShouldNotify` and `DelayMinutes`. For `DLY` with an estimate, only `Flight.DelayNotifiedDepartureUtc` decides — the estimate the last delay push went out for: push when there's none, or when the estimate is at least `DelayThreshold` later, and remember it. `statusChanged` doesn't count there, so a delay bouncing around the threshold through a silent `SCH` or `UNK` doesn't push on every return to `DLY`. A status travelers do hear (`DEP`, `ARR`, `CAN`, `DIV`) clears the remembered estimate, so a reinstated flight's new delay is news. Every other status pushes only when `statusChanged`, so a corrected `actual_out` on `DEP` records the event without a push. The minutes count from AeroAPI's reported schedule, not the stored `ScheduledDepartureUtc`, which a retime leaves stale. `FlightStatusChangedNotificationHandler` skips an event whose `ShouldNotify` is false before any lookup, and a delay push says how late the flight is ("Your flight is delayed by 40 min.") — minutes, so the message needs no timezone or locale. The remembered estimate belongs to the flight, not a traveler: it's set even when nobody received the push, so a traveler who starts tracking, or turns notifications on, after a delay push hears nothing until the delay grows 15 minutes. A flight already delayed when this shipped has no remembered estimate, so it pushes once when its estimate next moves; an unchanged estimate takes the known-status path (#351), which never pushes.

**Recording a status is one shared path (#386).** `FlightStatusApplier` (Application, `FlightSync/`) takes a `Flight` and an already-fetched `FlightStatusResult` and does everything after the provider call: resolving the status code to a row id with the `UNK` fallback, `ComputeDedupHash`, the known-status branch (#351), creating the `FlightStatusEvent`, and `Flight.ApplyStatusUpdate`, which decides the push (#352). `SyncFlightStatusCommandHandler` keeps what surrounds it — the traveler check, the manual-sync cooldown (#369), the budget guard (#303), the planner and the failure deferral (#356), the provider call itself, and `SaveChangesAsync`. It's a separate service because Phase 2 of #364 adds a second way a status arrives (an AeroAPI alert webhook), and a copy of these rules would drift: the dedup formula must never change, and the #351 and #352 rules are what decide whether a traveler's phone buzzes. **The applier never saves** — the caller owns the unit of work — and it makes no provider call, so it can't spend money. The `source` string it records and hashes is `FlightStatusSources.AeroApi` in `IFlightStatusProvider.cs` — the value `"AeroAPI"`, deliberately not the `"AeroApi"` spelling the config section and the named client use. Every path recording an AeroAPI status passes that one constant, and its value must never change: it is hashed into every stored dedup hash, so a caller spelling it differently would match nothing and record a second copy of every status.

**Search guard:** `AeroApiFlightSearchProvider` refuses any query that is not anchored on **both** ends of a route or on a flight number long enough to push down as `airline`+`flight_number` (≥ 2 chars). A single-airport query is ~700 rows in one call, and destination-only is worse than origin-only: with no origin there is no zone to anchor a local day on, so it runs over the widened 3-day window. The validator blocks these at the API edge; this guard is the backstop for every other caller.

**`links.next` is untrusted.** The `"AeroApi"` client attaches `x-apikey` to every request regardless of host, so a paging link is followed only if it resolves *underneath* `HttpClient.BaseAddress` — which rejects absolute, host-rooted and `../` links in one test. (Do not test "does it parse as absolute": `Uri.TryCreate("/schedules/…", UriKind.Absolute, …)` succeeds on Unix as a `file://` URI and would reject AeroAPI's own ordinary links.)

**Usage and spend come from the provider, never from a local meter.** `GET /admin/usage/aeroapi` proxies AeroAPI's own `GET /account/usage` via `AeroApiAccountUsageProvider` (same named client, same throttle, same `AeroApiResponse` error mapping), cached 10 minutes — FlightAware's own refresh cadence — under the resolved range. Do not reintroduce a local call-counting table (attempted and closed in PR #294): FlightAware bills per **page**, not per call, and bills **failed** calls too, so anything counted and priced locally is wrong in both directions and can never be reconciled against the invoice. `operation` arrives pre-normalised upstream, and `/account/usage` is itself billed at $0.00. The query defaults to the current UTC month to date with the end floored onto the 10-minute cache grid — an unrounded "now" would change the cache key on every request and spend a metered call each time — and its validator rejects a start older than AeroAPI's one-year history cap up front. `AeroApi:MonthlyBudgetUsd` and `AeroApiThrottleGate.NextSlotUtc` reach the Application handler through `IAeroApiBudgetOptions` / `IAeroApiThrottleObserver` (the `IFlightSearchHorizonOptions` translation pattern); both are attached fresh per request rather than cached alongside the upstream payload.

**The budget guard enforces `AeroApi:MonthlyBudgetUsd` (#303).** `ProviderBudgetGuard` (Application) compares this month's `TotalCostUsd` — the figure the panel's gauge uses — with the budget: `Normal` below `AeroApi:SoftLimitRatio` of it, `SoftLimit` from there, `Exhausted` at the budget. It reads the usage report through `AeroApiUsageCache`, the same range and cache entry as `GET /admin/usage/aeroapi`, so the gauge and the guard share one free upstream call every 10 minutes and can't disagree. It fails open: a failed read is `Normal` and is remembered for 10 minutes, because a failed read almost always means AeroAPI itself is failing, when the calls the guard would hold back fail anyway, and retrying it on every check would spend a throttle slot each time. A month's first 10 minutes are `Normal` without a read, since the usage range can't be cached before then. **Search:** `AeroApiFlightSearchBudgetDecorator` sits between `AeroApiFlightSearchCachingDecorator` and `AeroApiFlightSearchProvider`. From `SoftLimit`, a cached search is still answered, and a cache miss gets a 503 naming the budget before any request, including the timezone lookups the search would have made. Phase 3's fallback provider is meant to answer those misses instead. **Status sync:** `SyncFlightStatusCommandHandler` never reads the budget for a flight in Fast mode, which always gets its call. From `SoftLimit`, a Live flight's next sync is planned at twice `FlightSync:Interval`. At `Exhausted`, the background loop makes no call for a flight that isn't in Fast mode and plans it again at that doubled interval (capped at when Fast starts), without counting it as a failure. A person's sync of such a flight gets a 503 naming the budget rather than a silent `{ updated: false }`, since the stored status can be an hour old.

**CI results come from GitHub, through the API (#332).** `GET /admin/ci/runs` lists the CI workflow's runs and `GET /admin/ci/runs/{id}/tests` reads a run's `test-results.json` from the `test-results` artifact `ci.yml`'s Report step uploads, so the panel never holds a GitHub token. `GitHubCiRunProvider` gets two named clients and **only `"GitHub"` carries the token**: an artifact download answers 302 with a signed blob-storage URL, which is fetched with `"GitHubArtifactDownload"`, a client with no credentials. Neither client follows redirects itself, so whether the token reaches another host is decided by this code rather than by a handler's redirect rules; `GitHubDependencyInjectionTests` pins both, including against a registration that passes the token client as the download client. `GitHub:Token` is optional: without it the app still starts and both routes answer 503. The run list is cached 60 s. A report is cached for an hour **by artifact id, not run id**, because a re-run keeps its run id but uploads a new artifact. "No artifact yet" is never cached, so a run's report shows up as soon as it's uploaded. The downloaded archive (50 MB) and the decompressed report (20 MB) are both capped, since a zip entry's declared size can lie. The signed download URL is never logged. Upstream failures map like AeroAPI's: a rejected token or a 404 on the workflow is our configuration (500; GitHub answers 404 for a private repository the token can't see), a rate limit is 503 (403 counts only with `x-ratelimit-remaining: 0`, `Retry-After`, or a message saying so), anything else is 502.

**The typed admin drill-downs mask, and so do the older typed traveler endpoints (#321).** `GET /admin/travelers/{id}/detail` and `GET /admin/flights/{id}/detail` exist for what a generic browser cannot assemble — a traveler with their device tokens, tracked flights and memberships in one call, and a flight with its `FlightStatusEvent` history. All of `GET /admin/travelers`, `GET /admin/travelers/{id}` and the two drill-downs mask from `SensitiveProperties`, in the Application handler, exactly as the browser does — `GetAllTravelersQuery` and `GetAdminTravelerByIdQuery` share one `AdminTravelerResult.FromEntity` factory so the two typed routes cannot drift on whether `Email` is masked the way they did before #321 (both returned it in the clear, one route away from A4's masking and A5's audited reveal). `AdminResultMaskingCompletenessTests` (Application.Tests) is the backstop against this recurring: it fails the build the moment a new admin `*Result` record exposes a property name registered in `SensitiveProperties` without a reviewed, deliberate masking decision recorded alongside it.

**A capped collection fetches one row past the cap.** Both drill-downs bound their growing list — 50 status events, 50 tracked flights — with a real SQL `LIMIT` keeping the newest rows, and report a truncation flag. The flag is computed by asking for `Max + 1` and testing `> Max`, never by inferring from `Count == Max`: that inference reports a flight with *precisely* 50 events as truncated when it is complete, sending an operator to the generic browser for rows that are not there. The probe row is never returned. Only `traveler_flights` and `flight_status_events` are capped — memberships are schema-bounded by `UNIQUE(TravelerId, ProgramId)` and device tokens are tiny, so both stay whole. A4's browser pages all of these in full, so the drill-down is the recent view and the browser is the archive.

**Deleting a device token is not revoking a device.** It stops APNs pushes to that token; the client re-registers on next launch. The delete is audited for free by `AdminAuditInterceptor` because it goes through the tracked-entity path — which is exactly why it must stay there. Switching it to `ExecuteDeleteAsync` would bypass the `SaveChangesInterceptor` and silently stop auditing, and `FlightAssistantWebApplicationFactory` strips the interceptor entirely (#319), so an API-level test would still pass. Audit assertions for this belong in the Infrastructure suite, PostgreSQL-backed, where the interceptor is genuinely attached.

**Revealing a masked value is audited before the value is returned.** `POST /admin/data/{table}/{id}/reveal` hands back one full value of a column the browser masks — and the ordering is the feature: read the value, construct the `AdminAuditLog` row, `SaveChangesAsync`, **then** return. A failed save is a 500 with no value, because an unaudited reveal is the one outcome the endpoint must never produce. The row is written **explicitly**, not by `AdminAuditInterceptor`: a reveal is a read, nothing enters the `ChangeTracker`, so there is nothing for the interceptor to observe (it skips `AdminAuditLog` entries anyway, and its append-only guard rejects only `Modified`/`Deleted`, so an `Added` row passes). **The revealed value is never stored in that row** — `Before`/`After` stay null and `Summary` omits it; writing it would put the plaintext back into `admin_audit_log`, defeating masking-on-write and making the audit table the exfiltration path the reveal audit exists to detect. Only columns registered in `SensitiveProperties` are revealable; anything else is a 400, since a reveal returning a non-sensitive value is just an alternate read path around the browser. `POST` not `GET` (it has a side effect), `Cache-Control: no-store`, no audit row on a 404, and an `admin-reveal` rate limit partitioned by actor (`oid` → `sub` → IP, never IP alone) on that one route.

**`EntityId` comes from the loaded row's EF key metadata, never from the caller's string.** A caller-supplied `{C118FC0E-…}` would otherwise persist braced and uppercase while `AdminAuditInterceptor` writes the canonical lowercase form, and an auditor's `WHERE entity_id = '<guid>'` would silently miss those rows. Both writers reading the key from the same EF metadata is what stops them drifting; normalising strings by hand would need keeping in sync forever.

**The admin data browser is a whitelist, and the whitelist has a keeper.** `GET /admin/data/tables` and `GET /admin/data/{table}` read all 20 entity types through `BrowsableTables` (Application), an explicit registry of slug → CLR type → exposed columns. Explicit rather than reflection over `dbContext.Model`, so a new entity or column must be classified deliberately — but that only holds because `BrowsableTablesModelCompletenessTests` fails when the registry drifts from the model **in either direction**: a new `DbSet` left unclassified, or a new mapped property on an already-browsable entity left off both the exposed and excluded lists. Without those guards the registry would silently go stale, which is strictly worse than the reflection it replaced: reflection would at least have shown the new table. `NotBrowsable` carries a reason string so an exclusion is a decision, not an oversight. The tests live in `Infrastructure.Tests` because they need `ctx.Model` and `Application.Tests` must not gain an Infrastructure reference.

**`BrowsableTables` says what is exposed; `SensitiveProperties` says what is masked.** The browser projects every registered column, then replaces any value whose `(type, property)` is registered sensitive with `"<redacted>"` **before it leaves the API** — masking is in the Application handler, not the repository, which stays a generic paginated reader. The same projection renders enum columns as their **names** (#392) — `SyncMode` as `"Fast"`, audit `Action` as `"Update"` — because the repository projects materialised properties by reflection, so an enum arrives boxed and `System.Text.Json` would otherwise write its underlying number, unlike every other admin surface. The filter already parsed names (`ConvertFilterValue` → `Enum.Parse`), so this makes the grid agree with what it accepts. Sorting still orders by the underlying value in SQL — declaration order, not alphabetical — because sorting names in memory would break paging. Sensitivity is never duplicated onto `BrowsableTables`: one registry serves the audit interceptor's before/after snapshots, this projection, and A5's reveal, because two PII lists that both have to be right drift the way CLAUDE.md already describes for validator format rules — except that drift leaks PII. **A sensitive column is rejected in both `sort` and `filter` with a 400**: filtering it would make the browser an oracle for guessing a masked value one character at a time, and ordering leaks ordering.

**Column names are validated against the registry before reaching `EF.Property<object>()`, and matching is `Ordinal`.** Do not "improve" that to case-insensitive on its own — `SensitiveProperties.IsSensitive` is also Ordinal, so a case variant would pass the exposure check while failing the sensitivity check, making a sensitive column sortable. The safe version canonicalises the incoming name against the registry first and uses the canonical form for *both* checks.

**One correlation id, everywhere (#319).** `CorrelationIdMiddleware` accepts a valid `X-Correlation-Id` from the caller or mints one, and that single string reaches four places: the response header, every Serilog line (`LogContext`), ProblemDetails' `traceId`, and `admin_audit_log.TraceId`. Before this, three identifiers competed and the two that most needed correlation used the worst one — `Activity.Current?.Id`, which is **null for the entire request** unless `ApplicationInsights:ConnectionString` is set, because nothing registers an `ActivityListener` otherwise. So the audit log's correlation column was null on every row in every environment without App Insights, and ProblemDetails fell back to `HttpContext.TraceIdentifier`, which appears in no log line at all. A user quoting the id from a failed request now lands you on the logs *and* the audit row. It travels by `HttpContext.Items` rather than a scoped service because `GlobalExceptionHandler` is registered as a singleton and could not take a scoped dependency without a captive-dependency problem; Application and Infrastructure, which cannot see `HttpContext`, read it one hop later from `IAdminContext.CorrelationId`, populated by the `/admin` endpoint filter.

**Every admin write is audited in the same transaction as the write.** `AdminAuditInterceptor` reads the `ChangeTracker` on **`SavingChangesAsync`** — deliberately unlike `DomainEventDispatchInterceptor` next to it, which fires on `SavedChangesAsync`, *after* commit. An audit row that can roll back independently of the change it describes is worse than no audit row. Actor comes from a scoped `IAdminContext` (defined in **Application**, not API — Infrastructure has to resolve it and cannot reference API), populated by an endpoint filter on the `/admin` group; **no actor means no row**, so ordinary traveler traffic through the same `DbContext` is untouched. The **append-only guard sits above the actor gate**, so tampering with an audit row throws no matter who is saving. Actions derive from the tracker — `Verify` is a `Modified` whose changed properties are non-empty and entirely contained in the `IVerifiable` set, derived from the interface rather than a name list — with `Import` the single explicit override, because an upsert of 500 airports is otherwise indistinguishable from 500 manual edits and must be findable as one event. The rule is a subset, not an exact match (#355): `VerificationIssue` stays null→null on an ordinary `Verify()`/`Unverify()` call, so EF never marks it modified, and an exact-match rule would then miss the set on every such save and log it as an `Update` instead. Verifying *and* changing another property in the same save is still correctly an `Update`, since the modified set then contains a property outside `IVerifiable`.

**Sensitive values are masked on write and never stored.** `Traveler.Email`, `DeviceToken.Token` and `TravelerLoyaltyMembership.AccountNumber` record `"<redacted>"` in both `Before` and `After` — the fact of the change is captured, the value is not. Otherwise the audit log becomes a second, unprotected copy of exactly the PII A5 guards, reachable through a different endpoint, plus a GDPR-erasure liability. **The accepted cost: a redacted previous value is unrecoverable.** The classification lives in **one** `SensitiveProperties` registry in Application that A4's masking and A5's reveal also read; two copies of a PII list is the drift CLAUDE.md already names for validator format rules, except here the drift leaks PII. The placeholder string itself is the same kind of shared constant — `SensitiveProperties.RedactedPlaceholder` — read by this interceptor, `GetBrowsableDataQueryHandler` and `GetAdminTravelerDetailQueryHandler` alike, so a divergent literal in any one of them can never render a masked value that no longer looks masked. Look it up by `entry.Metadata.ClrType`, never `entry.Entity.GetType()` — a proxy type misses the registry, and a missed lookup is a silent leak.

**`AdminAuditLog.EntityId` is null for creates of store-generated-key entities.** Npgsql assigns identity keys during `SaveChanges` via `INSERT … RETURNING`, so at `SavingChanges` time the key does not exist, and recovering it would mean writing post-commit and forfeiting the whole transactional guarantee. It previously recorded EF's temporary sentinel (`-2147482647`), which reads as a real id and collides across every create of every type. Such a row is identified through `After`, which carries the created entity's full property set.

**`AdminAuditLog.TraceId` carries the request's correlation id, not `Activity.Current?.Id` (#319).** Before this fix there were three competing identifiers — `CorrelationIdMiddleware`'s id (always present: response header + every Serilog line), `Activity.Current?.Id` (only present with App Insights configured), and `HttpContext.TraceIdentifier` (always present, but in no log line) — and both `TraceId` and ProblemDetails' `traceId` used the one least likely to exist, making the audit log's own correlation column uncorrelated with anything an operator could actually search. `CorrelationIdMiddleware` now stashes its id on `HttpContext.Items` (`CorrelationIdMiddleware.ItemsKey`); the `/admin` endpoint filter (`Program.cs`) copies it onto `IAdminContext.CorrelationId` — Infrastructure and Application cannot see `HttpContext`, so this is the same routing `ActorId` already uses — and both audit writers (`AdminAuditInterceptor`, `RevealValueCommandHandler`) resolve `TraceId` as `_adminContext.CorrelationId ?? Activity.Current?.Id`, correlation id first. `GlobalExceptionHandler` reads the same `HttpContext.Items` value for ProblemDetails' `traceId`. **This changed an existing response field's value**: `traceId` now carries the 32-hex correlation id instead of a W3C trace id or ASP.NET connection id — intended, since a `traceId` absent from every log line was never useful, but visible to any client that was parsing the old format.

**The admin drill-downs (#322) are a new route each, not an extension of an existing one.** `GET /admin/travelers/{id}/detail` returns the traveler with its device tokens, tracked flights (joined server-side with their `Flight` row, including both airport ids so a caller can draw the route without a second call) and loyalty memberships in one call, masking `Traveler.Email`, `DeviceToken.Token` and `TravelerLoyaltyMembership.AccountNumber` — all three registered in `SensitiveProperties` — the same way `GetBrowsableDataQueryHandler` does: in the Application handler (`GetAdminTravelerDetailQueryHandler`), never the repository. It does not extend the existing `GET /admin/travelers/{id}`, whose `AdminTravelerDto` is the narrower row shape (no device tokens, tracked flights or memberships — both mask `Email` the same way since #321): bolting relationship data onto that route would also have to silently change its response shape for anyone already calling it, and a single route whose shape depends on nothing visible in the request is worse than two routes with two clear, separate contracts. `GetAdminTravelerDetailQueryHandler` calls three repositories — `IAdminTravelerRepository`, `IFlightRepository`, `ILoyaltyRepository` — each resolving its relationship server-side (an `Include`, or a LINQ `Join`) in one query apiece, a fixed count that does not grow with how many tokens/flights/memberships the traveler has; the read side of each is `AsNoTracking`. Memberships (`ORDER BY ProgramId`, in `LoyaltyRepository`) and device tokens (sorted by `LastSeenUtc` in the handler itself, since they load through the traveler's own `Include` rather than a separate `IQueryable`) both carry a deterministic order — PostgreSQL gives none for free, and an admin panel re-rendering the same traveler in a different order between two identical calls is churn with no cause. Tracked flights is the one relationship of the three actually capped: `traveler_flights` has no retention/purge path and grows monotonically with usage, unlike memberships (schema-bounded by `UNIQUE(TravelerId, ProgramId)`) or device tokens (small in practice). `IFlightRepository.GetRecentTravelerFlightsAsync` caps it at `GetAdminTravelerDetailQueryHandler.MaxTrackedFlights` (50) via a server-side `LIMIT`, newest-serviced first, and `AdminTravelerDetailResult.TrackedFlightsTruncated` tells a caller when that cap actually cut rows off — `GET /admin/data/traveler-flights` (A4) already pages the full relationship, so the truncation flag is what points a caller from the "recent" drill-down view to that archive.

**`GET /admin/flights/{id}/detail` derives "current status" from the newest `FlightStatusEvent`, and caps the history it returns.** There is no separate current-status column on `Flight` — `CurrentStatus` is simply `StatusHistory[0]`, since `IFlightRepository.GetRecentFlightStatusEventsAsync` already returns events most recently recorded first (by id, #351 — not by effective time, which can move backwards when an estimate returns to an earlier value). The history is capped at `GetAdminFlightDetailQueryHandler.MaxStatusHistory` (50) via a server-side `LIMIT`, not the unbounded `GetFlightStatusEventsAsync` the traveler-facing status endpoint already uses — a flight tracked for weeks and polled every couple of minutes accumulates rows without bound, and this "one call" detail view must not load all of them just to show the recent ones. `AdminFlightDetailResult.StatusHistoryTruncated` (fetch `MaxStatusHistory + 1`, test `> MaxStatusHistory` — see "A capped collection fetches one row past the cap") is what lets a caller tell "exactly 50 events, capped" apart from "exactly 50 events, full stop" — the cap alone is otherwise documented only in Swagger/XML, invisible in the JSON itself — and points to `GET /admin/data/flight-status-events` (A4) for the rest. Each row also carries the provider's raw status text — e.g. AeroAPI's `"En Route / On Time"` — extracted from `FlightStatusEvent.RawPayloadJson` (the whole raw AeroAPI row `AeroApiFlightStatusProvider` already stores) rather than a column of its own; null — "where recorded" — for a row with no payload at all, such as a manually-created event. Because `FlightStatus` has no public constructor (only EF's own materialiser ever populates its navigation), the per-event mapping can only be proved against a real `Include`, not a mock — see `AdminDrilldownRepositoryTests` (Infrastructure.Tests, PostgreSQL-backed), which is also where this endpoint's "one query, not N+1" guarantee is proved by actually counting SQL statements via a `DbCommandInterceptor`, since InMemory never issues a `DbCommand` at all.

**The device-token delete's audit-row guarantee is tied to the handler itself, not just to the interceptor.** `AdminAuditInterceptorPostgresTests.Handle_DeviceTokenDeletedThroughTheRealHandler_WritesADeleteAuditRow` constructs the real `DeleteDeviceTokenCommandHandler` against a real, audited `AdminTravelerRepository` — unlike its neighbour in the same file, which proves the interceptor audits a tracked `DeviceToken` removal by hand-rolling the same two lines the handler happens to contain today. That distinction is not cosmetic: measured by temporarily deleting the handler's `traveler.RemoveDeviceToken(...)` call, the hand-rolled test still passed 6/6 while this one failed — a future change that swapped the delete to `ExecuteDeleteAsync` (works on PostgreSQL, throws on InMemory — #295) would bypass the change tracker, and this interceptor, exactly the same way, silently losing the audit trail while the API-level test and every other existing test kept passing.

**`DELETE /admin/travelers/{travelerId}/device-tokens/{tokenId}` is audited for free, and is explicit that it is not a device revocation** (it only stops APNs pushes to that token; the client re-registers on next launch). `DeviceTokenConfiguration`'s FK to `Traveler` is `OnDelete(Cascade)`, so removing a token from a loaded, tracked `Traveler.DeviceTokens` collection marks that `DeviceToken` entry `Deleted` in the change tracker — `AdminAuditInterceptor` picks it up on its own; `DeleteDeviceTokenCommandHandler` never builds an audit row itself. Removing a token also touches the parent `Traveler` (`RemoveDeviceToken` calls `SetUpdated()`), so one delete actually produces *two* audit rows — a `Delete` for the `DeviceToken` and an `Update` for the `Traveler` — both correct, since both entities really did change in that `SaveChanges` call. An unknown traveler or an unknown token both 404 before `SaveChangesAsync` is ever called, so neither produces a row. This is deliberately a new command (`Commands.Admin.Travelers.DeleteDeviceTokenCommand`), not a reuse of the traveler-facing `Commands.Travelers.RemoveDeviceTokenCommand`: that handler treats an unknown token as a silent no-op and always saves, which would give every unknown-token call here a 204 and (harmlessly, since nothing changed) no audit row — a "success" response that is the opposite of the required 404.

**Date query parameters on admin endpoints bind `DateTimeOffset?`, never `DateTime?`.** A bare `?fromUtc=2026-09-01` with no `Z` or offset binds as `DateTimeKind.Unspecified`, which Npgsql refuses against a `timestamptz` column — an unhandled `ArgumentException` and a 500. **This has now cost two bugs** (`/admin/usage/aeroapi` and `/admin/audit`), both invisible to the API test suite because it runs on the InMemory provider, which accepts an Unspecified `Kind` happily. Any endpoint taking a date needs either a `DateTimeOffset?` parameter or a PostgreSQL-backed test — the #295 harness exists for exactly this class of divergence.

**`/admin/health` is the operator view; `/health/ready` is a probe.** `GET /admin/health` runs `HealthCheckService.CheckHealthAsync()` with **no predicate**, so the `external` checks (`aeroapi`, `apns`) that `/health/ready` deliberately excludes are included — App Service restarts the app on a 503, so a flaky FlightAware host must never be able to cause one, which is exactly what makes `/health/ready` useless to an operator. It returns **200 even when the overall status is `Unhealthy`**: a report, not a probe, and a non-2xx makes the panel's error handling swallow the body that explains the failure. It costs no metered query — `AeroApiHealthCheck` builds a *bare* `IHttpClientFactory.CreateClient()` and sends a HEAD, so it carries no `x-apikey` and passes through no `AeroApiThrottlingHandler`; do not "improve" it into a real API call. Uniquely among the admin endpoints it is mapped **without MediatR**, because every input is a hosting artifact (`HealthCheckService`, `IHostEnvironment`, `IConfiguration`, the entry assembly, the `DbContext`'s migration lists) and Application-side translation interfaces for them would buy nothing testable; the shaping lives in `AdminHealthReportBuilder` instead. Exception detail, and `flightSync.lastError`, follow the `DiagnosticDetail` convention and render outside Production only; `redisConfigured`/`appInsightsConfigured` are booleans precisely so no connection string can escape through a diagnostics endpoint.

**"Cannot tell" is not "nothing pending".** `AdminHealthMigrationsDto.Available` is `false` both on a non-relational provider *and* when the migration-history read throws. `Database.IsRelational()` answers a **provider** question — it is `true` for Npgsql whether or not Postgres is reachable — but `GetApplied`/`GetPendingMigrationsAsync` need a live connection, so a database outage threw a raw `NpgsqlException` that took the whole report down with it, returning 500 at exactly the moment an operator needs the page, while the `database` check beside it degraded gracefully via `CanConnectAsync`. Both failure modes now report `Available: false` with a gated reason rather than an empty `Pending` list, which would be a different and much stronger claim.

**`FlightStatusSyncBackgroundService` publishes a heartbeat.** It swallows per-flight exceptions and retries on batch failure, so a service failing every cycle was indistinguishable from a healthy one from outside. `FlightSyncHeartbeat` (API layer — writer and reader both live there, so no cross-layer interface) publishes an **immutable `FlightSyncSnapshot` by atomic reference write**; that, not the lock, is what makes a concurrent reader safe. The lock serialises the read-modify-write inside the `Mark*` methods so a second writer, if one is ever added, cannot lose an update. `FlightsProcessed` counts flights **attempted** and `FlightsFailed` the subset that threw — a batch completing with failures is still outcome `Success`, because the *batch* ran. When `FlightSync:Enabled` is false the heartbeat stays at `NeverRun` with null timestamps, which must read as *disabled*, not *broken*. It also records how long each run took (#353) — `FlightSyncSnapshot.LastRunDuration`, surfaced as `flightSync.lastRunDurationSeconds` on `/admin/health`, null until a run completes so "never run" cannot read as "instant". The background service measures it with its injected `TimeProvider`, not a `Stopwatch`, so a `FakeTimeProvider` test asserts an exact value, and the heartbeat stays a plain state holder with no clock. A run longer than `FlightSync:LoopInterval` logs a warning: `PeriodicTimer` starts the next run immediately, so nothing breaks, but each flight is then polled less often than the interval suggests — which is invisible without it.

**Each tracked flight is synced on its own schedule (#356).** `FlightSyncPlanner` (Application) gives a flight a mode from its times, status and tracking, first match wins: none (no traveler tracks it); `Stopped` (`FlightSync:StopAfterArrival` after its actual arrival or `CancelledAtUtc`, or `StopWithoutArrivalAfter` after an arrival that is never reported); `Fast` (from `FastWindowBeforeDeparture` before the *estimated*, else scheduled, departure; every `NearDepartureInterval`); `Live` (from `AeroApi:StatusWindowFutureDays` before the *scheduled* departure, the first moment `/flights/{ident}` can answer, #343; every `Interval`); `Schedule` (further out). The next sync is capped at the moment the mode would change, so a stored mode is at most one loop stale. `FlightStatusSyncBackgroundService` wakes every `LoopInterval` and sends `SyncFlightStatusCommand(null, id, SyncTrigger.Scheduled)` only for tracked flights with `NextSyncDueUtc <= now` or no mode at all (never planned: tracked by an older build between the migration and the app deploy, or a track racing the last untrack), unplanned first, then oldest due, **each in its own DI scope** so a flight that fails part-way can't be saved by the next one's `SaveChanges`. A loop sync of a flight that's no longer due (a manual sync ran after the loop listed it) makes no call and saves nothing. The loop never calls AeroAPI for a Stopped flight; an admin or traveler sync still does, because a person asked. `ActualArrivalUtc` is AeroAPI's gate arrival (`actual_in`), falling back to runway arrival (`actual_on`), which is often all AeroAPI reports; without the fallback a landed flight stops only by `StopWithoutArrivalAfter`. Schedule-mode flights make no call yet (the `/schedules` check is step 2 of #349) and are next due when Live starts. `LastSyncedUtc` records every call that returned, empty or duplicate included; a loop call that throws keeps the flight's mode and moves its next sync one interval on without marking it synced, because a failed call can still be billed and retrying every loop would cost a call a minute; a person's call that throws saves nothing. Tracking an unplanned flight makes it due now; the last untrack clears its mode but keeps `LastSyncedUtc`. Deleting a traveler doesn't clear plans; the loop ignores untracked flights, so that costs no calls. A traveler's manual sync (`SyncTrigger.Traveler`) of a flight synced less than `FlightSync:ManualSyncCooldown` ago (default 5 min) returns false without calling the provider (#369). It reads the flight's own `LastSyncedUtc`, so every traveler tracking the flight shares the cooldown; admin and scheduled syncs ignore it. A traveler's call starts the cooldown as soon as it's attempted, through a per-flight marker in `ICacheService` that expires after the cooldown, so a failed call, or a second request during the throttle wait, makes no further billed call. The marker is shared across instances only when Redis is configured, and a cache outage fails open. `POST /flights/{flightId}/sync` also carries the `flight-sync` rate limit, partitioned by caller (oid → sub → IP) like `loyalty-programs` and `admin-reveal`; `RateLimiting:FlightSync:PermitLimit` and `WindowSeconds` default to 6 per 60 s. The limiter keeps its counts per app instance, so a scale-out multiplies the effective limit by the instance count.

**A traveler's tracked flights are capped (#380).** A traveler can have at most `FlightSync:MaxActiveTrackedFlightsPerTraveler` (default 20) tracked flights the status sync still polls. `IFlightRepository.CountActiveTrackedFlightsAsync` counts them in SQL as the negation of `FlightSyncPlanner`'s Stopped rule, from the flight's times and status rather than its stored `SyncMode`, so a stale mode can't hold a slot; `FlightRepositoryTests` checks the count against the planner so the two rules can't drift, and `GET /flights` reports that same rule per flight as `countsTowardCap` (#396), computed from `FlightSyncPlanner.IsStopped` — which is why that method is public rather than private. A slot frees `StopAfterArrival` after a landing or cancellation, `StopWithoutArrivalAfter` after the arrival time when no landing is reported, or at once on untrack. `TrackFlightCommandHandler` checks it after the airline and airport lookups and before creating the flight row, so a refused track (409, on both `POST /flights` and the admin route) writes nothing, and a flight the traveler already tracks still returns 201 at the cap. It bounds how many flights one account keeps polled, not how often a traveler tracks — that is the `flight-track` rate limit's job (#390), 10 per 60 s partitioned by caller (oid → sub → IP), configured under `RateLimiting:FlightTrack` and applied to `POST /flights` alone; tracking makes no provider call, so what it bounds is the rate at which one caller creates flights the sync loop then polls. Concurrent requests can still overshoot the unlocked count, and like every policy the limiter counts per app instance. Travelers already above the cap keep their flights.

**Forwarded headers are applied first (#371).** The API runs on Linux App Service, which terminates TLS and proxies every request, so without `UseForwardedHeaders` `HttpContext.Connection.RemoteIpAddress` is App Service's front end and every IP-partitioned rate limit lumps all callers into one bucket. `ForwardedHeadersOptions` forwards `X-Forwarded-For` and `X-Forwarded-Proto` with no known-proxy list (the front end's addresses aren't fixed) and `ForwardLimit = 1`, so only the rightmost `X-Forwarded-For` entry — the one the front end appended — is used; a client sending its own header can't pick its bucket. `UseForwardedHeaders()` is the first middleware. When `ASPNETCORE_FORWARDEDHEADERS_ENABLED` is `true`, the host adds the middleware itself and `Program.cs` skips its own call, checking the flag exactly as the host's `ForwardedHeadersStartupFilter` does, because running it twice would trust the client's own entry. Putting another proxy in front of App Service (Front Door, Application Gateway) would add a hop, and `ForwardLimit` and the proxy list would have to change with it; serving the app any way other than through App Service's front end (for example Kestrel exposed directly) would let a client set its own address. The `flight-search` policy (public and admin search) partitions by caller through `CallerPartitionKey` — `oid`, then `sub`, then that forwarded client IP — so signed-in travelers and admins each get their own 8-per-minute bucket and anonymous callers are counted per address. Like every policy, search included, the limiter counts per app instance.

**Shared outbound throttle:** `AeroApiThrottleGate`, a process-wide singleton applied via `AeroApiThrottlingHandler` to every AeroAPI `HttpClient`, spaces every outbound call — search or status — by `AeroApi:MinRequestInterval` (default 12 s, ≈5 requests/minute) to stay inside the personal tier's rate limit, regardless of which caller sent it. A caller reserves the next slot under a lock and waits it out without holding the lock; a reservation whose wait is cancelled is **released**, so an abandoned attempt never pushes the queue further out for everyone behind it.

**The throttle sits *inside* the resilience handler** (registered second, so it is closer to the transport) — deliberately, so every retry attempt is throttled too. The consequence is that a throttled wait of up to a whole `MinRequestInterval` elapses *within* the per-attempt timeout, so **every resilience timeout is derived from `MinRequestInterval`, never left at a library default or hardcoded** (`AeroApiOptions.AttemptTimeout` = interval + `TimeoutSeconds`; `TotalRequestTimeout` covers every attempt plus backoff; `CircuitBreakerSamplingDuration` ≥ 2× attempt; `HttpClient.Timeout` is a looser backstop outside all of it). With the library's 10 s default against a 12 s interval, every second call in an interval window was killed before it reached the transport, retried twice, and then failed the 30 s total timeout — surfacing as a 502 after a 30-second hang, and breaking every multi-page search from page 2 on. `AeroApiClientPipelineTests` sends real requests through the composed named client (on a `FakeTimeProvider`) because no test that only *resolves* DI objects, or that builds a bare `HttpClient`, can see this.

**Paging:** Input `PagedRequest(Page=1, PageSize=50)`, output `PagedResult<T>(Items, Total, Page, PageSize)`. Validated by `PagedRequestValidator` (Page ≥ 1, PageSize 1–200, and `(Page - 1) * PageSize` must fit in an `int` — the overflow boundary, not an arbitrary cap, #316). Repositories page through the one `PagedQueryableExtensions.Page` helper, which clamps offset to `[0, int.MaxValue]` as a backstop for callers that bypass the validator; never write `Skip((page - 1) * pageSize)` inline. Reuse `PagedRequestValidator` in query validators via `.SetValidator(new PagedRequestValidator())`. `GET /flights` is the one route that returns a wider envelope (`TrackedFlightsDto`): it adds `activeTrackedFlights` and `trackingCap`, which describe the **traveler**, not the page. A client cannot derive them from one page — tracked flights sort newest-service-date first, so future-dated cancelled flights can fill page 1 with non-counting rows while the slot-holding flights sit on page 2 (#397). The count comes from `CountActiveTrackedFlightsAsync`, the same method `POST /flights` enforces its 409 with, on the same clock reading as the per-row `countsTowardCap` flags.

**RefDataRepository:** Consolidates all reference data reads (airports, airlines, countries, alliances) in a single repository intentionally — see the file for rationale; planned to split later.

**Verification queue and claim model (#367).** `verification_requests` (`VerificationRequest`, Domain) is a database queue: an admin or a tracked flight enqueues a check, and `ReferenceVerificationBackgroundService`'s cycle claims and processes it. The claim is one SQL statement — a CTE selects up to `BatchSize` ids with `FOR UPDATE SKIP LOCKED` (a concurrent claimer skips a locked row instead of waiting and then re-claiming it) ordered by `trigger = 'flight'` first, then `requested_utc`, then `id`, and an `UPDATE … FROM` sets those rows `Running` with `started_utc = now`, `RETURNING v.*, v."xmin"` — so choosing rows and marking them claimed can never be split across two claimers. A partial unique index on `(entity_type, entity_key) WHERE status IN ('Pending','Running')` allows at most one open request per entity; `entity_key` is canonicalised first (a two-letter, upper-cased code for `Country`; a positive decimal `int` with no leading zeros for `Airport`/`Airline`) so the index sees one entity as one key, and a concurrent insert that loses the race to it is caught and counted as skipped, not an error. Each claimed row also carries PostgreSQL's own `xmin` system column as its concurrency token: `VerificationRequestProcessor` re-loads a request by id before acting on it and proceeds only while it is still `Running` with the claim's own `started_utc` (an ownership check that catches a stale claim before the save even runs), and a save against a stale `xmin` — typically a request reset as stuck and reclaimed since — throws, which the repository translates into `VerificationClaimLostException`: the outcome is "claim lost," nothing is written, no attempt is counted.

**The job's `system` actor, and why the queue table itself isn't audited.** Every DI scope the job saves through — claiming, processing, the stuck-request reset — carries `VerificationJobActor`'s `system` actor on that scope's `AdminContext`, so the job's `Verify`/`MarkVerificationFailed` writes to the entities it checks are audited exactly like an admin's. `AdminAuditInterceptor` skips `VerificationRequest` through its `NotAuditedTypes` set, as it skips `AdminAuditLog`: the request table is its own history (every status change is already a row in it), and auditing it under the job's actor would add an `Update` row per status change of every request in the queue.

**A stuck-request reset counts an attempt, not a free retry.** The 10-minute stuck-`Running`-to-`Pending` reset (`VerificationCycleRunner.StuckAfter`) is a single set-based `UPDATE`, so it counts an attempt for every row it touches and completes a row outright as `Error` (`Claim abandoned: no result recorded after N attempts`, N counting source errors too) once that reaches `MaxAttempts` — the same bound a source-error retry has, so a poison request or a crash loop can't cycle forever. When even *recording* a processing failure throws, the request is left `Running` with no attempt counted at all (`VerificationProcessOutcome.FailureUnrecorded`); this reset is what eventually reclaims it, and is the only place its attempt gets counted. A cache-release failure *after* a batch has already been processed and saved is different again: it raises `VerificationCycleFailedException`, the heartbeat is marked failed with that batch's real counts, and the loop continues on its next poll.

**A shutdown returns unfinished claims; a cycle asks which sources are in use only while one holds something.** When the job's token is cancelled mid-batch, `VerificationCycleRunner` returns the claim in progress and every later one to `Pending` — `started_utc` cleared, no attempt counted — through `ReturnClaimsToPendingAsync`: one statement guarded by `status = 'Running'` *and* each claim's own `started_utc`, so a claim another worker took over, or an outcome already saved, is untouched. It runs on its own 5 s `ReturnClaimsTimeout`, never the cancelled token, and a failure is only logged: the stuck reset stays the fallback. Without it a deploy spent an attempt on every unprocessed claim, and with `MaxAttempts = 1` turned them all into `Error`. Separately, every cycle ends with the release step, which asks for the source names in use in one `GetSourceNamesInUseAsync` query and skips it only when no source `HasCachedData` (nothing loaded, loading or failed). While a source's dataset is held inside its `Verification:IdleRelease` window (#378), each cycle — an idle one included — still runs that query; once nothing is held, an idle cycle costs only the reset and the claim.

**The `/admin/health` verification section degrades rather than fails.** `AdminHealthReportBuilder.BuildVerificationAsync` reads the heartbeat once. `PendingCount` is `null` when the count query throws — "cannot tell", not zero, like `AdminHealthMigrationsDto.Available` — and `LastError` renders outside Production only, per the `DiagnosticDetail` convention. `StuckAbandoned` and `FailuresUnrecorded` (#385) sit beside `RequestsProcessed`/`RequestsFailed` and follow the exact same rule: `MarkRunSucceeded` and the batch-aware `MarkRunFailed` overload set all four together for the cycle that just completed, while the plain `MarkRunFailed(ex, next)` — a cycle that failed before it processed a batch — leaves the previous cycle's values in place rather than zeroing them, so a cycle that fails early still shows what the last cycle that actually ran saw. With `Verification:Enabled` false the heartbeat stays `NeverRun` with null timestamps: disabled, not broken.

**An unexpected exception during processing stores only its type, in every environment.** Unlike `DomainException.DiagnosticDetail`, gated to outside Production, `VerificationRequestProcessor.RecordUnexpectedFailureAsync` writes a fixed `"Unexpected error (<Type>); see logs"` to `verification_requests.error` regardless of environment — the column carries no Production gating of its own, and an EF/Npgsql/argument exception's *message* can carry a host, port, table or constraint name, so only the exception's type name is safe to store unconditionally. The full exception, with the request id and the cycle's own correlation id, goes to the logs instead.

**Verification sources load on demand and are reused for at most 24 hours.** `OurAirportsVerificationSource` and `MledozeCountriesVerificationSource` share one `VerificationDatasetCache` (download-once, reuse-then-release) and one `VerificationSourceDownloader` (send-then-parse under one deadline): a dataset downloads only on the first `LookupAsync` call that needs it — never at construction or DI-resolution time — is reused for 24 hours, and is dropped by `IVerificationSourceRegistry.ReleaseUnused` once `VerificationCycleRunner` finds no open request still names that source **and** it has gone unused for `Verification:IdleRelease` (#378; default 30 min, range 0–24 h — `0` releases it as soon as no open request does, the pre-#378 behaviour), checked after every cycle: a one-row check soon after another then reuses the download instead of repeating it. The idle period never extends the 24-hour maximum age — a dataset at or past it is dropped at the next release however recently it was used — and a cached failure is unaffected — it still expires only on `FailureCooldown` below, never kept for being recent. A load that finishes with no caller left waiting on it is stamped as last-used right then, starting its idle clock even though nothing has asked for it since. Concurrent callers needing the same stale-or-absent dataset share one download rather than each starting their own, but each caller's own cancellation only cancels its own wait — never the shared download, or any other caller's wait on it; a failed load is kept for `VerificationDatasetCache.FailureCooldown` (60 s, never longer than the first retry backoff), so every lookup inside it gets the same source error without a new download — before, a batch against a stalled upstream waited out the 3-minute deadline once per request, past the 10-minute stuck cutoff — and the first lookup after it downloads again; a release drops it, and a cancelled load is never kept. A dataset that parses but yields **zero** usable rows is a source error, never "not found for everything" — `NotFound` must mean the dataset loaded and simply has no row for this entity, not that parsing silently produced nothing. The named source clients carry no credentials, so following redirects is deliberate (both datasets are public), and each download creates its client from `IHttpClientFactory` instead of holding one. Downloads are capped (`MaxDownloadBytes`: 64 MB for OurAirports, 8 MB for mledoze): a declared `Content-Length` over the cap fails before reading, and a counting stream catches a body of unknown length without buffering it. A source error stores a fixed category plus the source name, HTTP status or cap — `Timed out downloading…`, `…download failed: HTTP <code>`, `Failed to download… (network error)`, `…larger than the <N>-byte download limit`, `Could not parse…`, `…had no usable rows` — never the upstream exception's message (a proxy error can name an internal address; a CsvHelper error quotes raw rows); the source logs the whole exception once per failed load. `mledoze` (`https://raw.githubusercontent.com/mledoze/countries/master/countries.json`) replaced the originally-planned `restcountries`: v3.1 was shut down, v5 needs an API key and has a monthly quota, and mledoze is the dataset restcountries itself was built from. It is licensed ODbL-1.0, which requires attribution to the dataset wherever it, or a work derived from it, is published. `MledozeCountriesVerificationSource` maps `Country.Name` from `name.common`, never `name.official` (the latter would mismatch nearly every well-formed row), and skips — rather than fails outright on — a record missing `cca2` or `name.common`. OurAirports likewise skips a malformed row (bad CSV data, a missing field, or a field count unlike the header's), while a missing or renamed column still fails the whole parse. Both log one warning per parse with the count and a small sample, not one per record.

**Domain verification guards (deferred from #355).** `Verify`/`MarkVerificationFailed` on all five `IVerifiable` implementations (`SeedableEntity`, `Lounge`, `LoungeProvider`, `LoyaltyProgram`, `LoyaltyProgramKind`) share one rule set, `VerificationGuard`: `verifiedBy`/`source` non-blank and within their column sizes (255/100 characters), `verifiedAtUtc` must be `DateTimeKind.Utc`, and `issue` non-blank and at most 500 characters — an `ArgumentException` at the call site instead of a database error at `SaveChanges`. `VerificationSummaryBuilder` truncates the job's own mismatch/not-found summary to fit before it ever reaches this guard.

**The six admin verification endpoints hold no rules of their own (#378, spec §4.1/§4.4).** `AdminVerificationEndpoints` binds, resolves the actor via `ClaimsPrincipalExtensions.GetAdminActorId()` (`oid` → `sub` → `"admin"`, the one copy of that rule — the `/admin` group filter reads the same two claims for `IAdminContext.ActorId` but keeps it null, since no actor there means no audit row), sends, and maps; every 400/404/409 comes from the commands' own validators and `DomainException`s. `POST …/accept-source` writes only the chosen source's differing columns — the `differences` entries whose `sourceName` matches — leaving already-matching columns in our own formatting, and its guard against a stale check reuses the checked-column comparer rather than raw string equality, so `İstanbul` still equals `Istanbul`. It reuses `UpdateAirportCommandValidator`/`UpdateAirlineCommandValidator` instead of a second copy of the edit rules, validating the *whole* merged row — so a pre-existing invalid value in a column the source never touched still blocks the accept with a 409 naming it; `Country` has no such validator, so its formats and lengths go unchecked on accept. A new unique code (Airport/Airline `Iata`/`Icao`, Country `Alpha3`/`NumericCode`) is looked up and refused with a 409 before the save if another row already owns it, but that is check-then-save: a genuinely concurrent write can still land between the check and `SaveChangesAsync` and hit the database's own unique index as a 500 — an accepted, documented race, not translated. A new Airport/Airline `CountryCode` missing from `countries` (a source can know `XK`) is refused the same way, since both tables reference it by foreign key and the edit rules check only its format. Accept also returns 409 while the entity has an open (`Pending`/`Running`) request: reference rows carry no concurrency token, so that newer check could save its `MarkVerificationFailed` over the accepted row. The request stays `Mismatch`, so accepting the same source again is a 409 only if that source had differences (those columns now hold its values); if it had none, it just verifies the entity again. `POST /admin/verification-requests` and `POST …/retry` both insert `verification_requests` rows, which `AdminAuditInterceptor.NotAuditedTypes` excludes (the table is its own history); `requested_by` is the only record of which admin asked. `verification-requests` is registered in `BrowsableTables`, exposing every mapped column except the `xmin` row-version shadow property, with nothing masked — `error` holds fixed categories and `requested_by` is an admin id, like `VerifiedBy`.

**Two more admin verification reads, and neither is audited (#385, R6).** `GET /admin/verification-requests?entityType=&entityKey=&limit=` is a "latest few" (R1), not a page: at most `limit` requests for one entity, newest first (`RequestedUtc` descending, then `Id` as the tiebreaker), no total and no `PagedResult` — the full history stays browsable at `GET /admin/data/verification-requests`, registered above. `limit` defaults to 5 and is validated to the range 1–50; `entityType` must be exactly `Airport`, `Airline` or `Country`; `entityKey` is canonicalised through the same `VerificationRequest.TryCanonicalEntityKey` the queue uses before matching, so a lower-case country code finds the upper-case row — all three are 400s when they don't parse. Each row's `sources`, `differences` and `sourceValues` come back typed (R2, via `VerificationJson`), not as the stored comma-joined or JSON strings the row itself holds, so the panel never re-parses what the API already understands. An entity with no checks yet is an empty 200, never a 404 — "nothing checked" is a normal answer, not an error. `GET /admin/verification-needs-attention` takes no parameters and always returns one entry per `VerificationEntityType` (`Airport`, `Airline`, `Country`), in enum order, with a count of `0` rather than an omitted entry (R3) — a row "needs attention" when it is unverified with a non-blank `VerificationIssue`, the state only the job's mismatch and not-found paths leave behind; a row that was simply never checked (`IsVerified` false, no issue) does not count.

**The data browser's `{column}:*` filter means "has a value" (#385, R4) — the newest member of a grammar `GetBrowsableDataQuery.Filter`'s own doc already spells out: exact match for a non-string column, case-insensitive `contains` for a string column, and `column:>=value` for "on or after" on a date column.** On a string column only, a raw value of exactly `*` matches a row whose column is non-null and non-blank after trimming; `*` anywhere else in the value (e.g. `Gold*`) stays a literal character to find by `contains`, and `*` on a non-string column stays an unparseable 400, same as before. It exists for the needs-attention dashboard card's drill-in link (`VerificationIssue:*`), but the rule lives in the general-purpose `BrowsableDataRepository.ApplyFilter`, so it works on any exposed string column across all 20 browsable tables, not only a verification one.

**`aeroapi` checks airports and airlines against AeroAPI itself, not a downloaded dataset (#401).** `AeroApiVerificationSource` calls `GET /airports/{id}` for `VerificationEntityType.Airport` and `GET /operators/{id}` for `VerificationEntityType.Airline` — AeroAPI's own term for an airline — over the same shared `"AeroApi"` named client flight search, flight status and the usage report already use, so a lookup is authenticated, retried and throttled by `AeroApiThrottleGate` exactly like every other AeroAPI call, not a second, ungoverned path to it; `CostPerRowUsd` is $0.015 per lookup. **Matching (R2):** ICAO — AeroAPI's own identifier — is preferred, falling back to IATA only when ICAO is blank, never as a second call after the preferred one fails; both blank is `NotFound` without sending a request at all. **Field mapping** (confirmed against a live capture, `FlightAssistant.Infrastructure.Tests/Fixtures/AeroApi/airport-sof.json` and `operator-baw.json`): airport's `code_iata`/`code_icao`/`name`/`city`/`country_code` (already two-letter) map to `Iata`/`Icao`/`Name`/`City`/`CountryCode`, `latitude`/`longitude` to `Latitude`/`Longitude`, and `elevation` to `ElevationFt` with no unit conversion (AeroAPI already reports feet); operator's `iata`/`icao`/`name` map to `Iata`/`Icao`/`Name`. **Errors (R3):** a 404 means AeroAPI has no row for the code — a real answer, mapped to `NotFound` — while every other failure (5xx, 429, a timeout, a network error, an unparseable 200) is a retryable `SourceError` with one of four fixed-category strings (`AeroApiVerificationSource.HttpStatusError`/`NetworkError`/`TimedOutError`/`ParseError`), never `DomainException.Message`, which is phrased for a traveler-facing flight response, not this column. The source does call `AeroApiResponse.ReadOrThrowAsync` — every other AeroAPI caller does, for its credential redaction and status-code logging, and there is no reason this one caller alone should reimplement that — but it captures the raw `HttpStatusCode` before that call, so the 404-vs-everything-else split never depends on parsing the exception. **Timezone cache (R7):** a successful airport lookup already paid for the call, so it opportunistically fills `AeroApiAirportTimezoneLookup`'s own cache — through that lookup's own `CacheKeyFor`, keyed by the response's own `code_iata`, not the requested lookup key — with the response's `timezone`; it never reads that cache back to answer a check. **No dataset (R6):** unlike `ourairports`/`mledoze`, `HasCachedData` is always false and `ReleaseCache` does nothing, since every lookup is its own billed call with nothing to reuse.

**R1 — an airline check no longer compares `CountryCode`.** `VerificationCheckedColumns`'s airline column list is `Iata`, `Icao`, `Name` only now; `CountryCode` came out because `aeroapi` — the airline source — reports an operator's country as a name (`"United Kingdom"`), never a code, and nothing in the app reads an airline's own `CountryCode` today. It stays a checked column on `Airport`, where every source reports a real two-letter code. The cost of leaving it unchecked is that an airline's country goes unverified — no different from before this source existed — and the column's own future (drop it, or add a name-to-code source) is tracked in #402, not decided here.

**The AeroAPI budget gate pauses verification instead of erroring it out (#401, R4/R5).** `VerificationRequestProcessor` asks `IProviderBudgetGuard.GetStateAsync` — the same guard flight search and status sync already use (#303), reading AeroAPI's own usage report, cached 10 minutes, pricing nothing locally — but only for a request naming `aeroapi` among its sources; a request naming only the two free sources is never gated, budget exhausted or not. `SoftLimit` and `Normal` proceed: the soft limit exists to slow flight traffic, not to stop an admin's explicitly requested check. `Exhausted` returns the claim to `Pending` through `ReturnClaimsToPendingAsync` — the same one-statement, claim-ownership-guarded path a cancelled cycle's unfinished claims already use (see "A shutdown returns unfinished claims" above) — touching only `status` and `started_utc`; `attempts`, `error` and `next_attempt_utc` are left exactly as they were, since a pause is the job declining to spend money it doesn't have, not a failure, and counting an attempt or writing error text is the one outcome this must never produce. `VerificationCycleRunner` remembers the first pause in a cycle (`aeroApiBudgetPaused`) so every later `aeroapi`-naming request in that same batch is paused on the flag alone, without a second guard read; a request naming only free sources ignores the flag and keeps processing regardless of it.

**A cycle that pauses is its own outcome, not a failure (#401, R4/R5).** `VerificationJobOutcome` gains `Paused` alongside `NeverRun`/`Running`/`Success`/`Failed`: `ReferenceVerificationBackgroundService` calls `VerificationJobHeartbeat.MarkRunPaused` instead of `MarkRunSucceeded` whenever `VerificationCycleResult.Paused > 0`, carrying the same processed/failed/stuck-abandoned/unrecorded counts plus `RequestsPaused`. `/admin/health`'s `AdminHealthVerificationDto.LastOutcome` therefore renders `"Paused"` distinctly from `"Success"` (nothing held back) and `"Failed"` (the cycle itself broke) — an operator sees why the queue isn't draining without reading logs. A cycle that pauses some requests and then separately fails releasing source caches still reports that batch's real `Paused` count through the batch-aware `MarkRunFailed` overload, the same way it already reports the other counts.

**Tracking a flight queues checks for its reference rows, and cannot fail tracking (#410, the flight-tracking trigger, step 10).** `Flight.MarkTracked` raises `FlightTracked` (Domain) on every track request — a new tracking link or a repeat — and `TrackFlightCommandHandler` now calls `SaveChangesAsync` unconditionally, so `DomainEventDispatchInterceptor` dispatches the event even when nothing else changed (R1): a repeat track can still find the airline or an airport gone stale since the last time this flight was tracked. `FlightTrackedVerificationEventHandler` (Application) is the sole subscriber: it loads the airline and both airports by id, never in a loop (R8), resolves their distinct country codes (R6), and queues at most three `IVerificationQueue.EnqueueAsync` calls — one per entity type, keys batched, never one call per row (R7) — with `estimatedCostUsd` summed from `IVerificationSourceRegistry`. One `try`/`catch` wraps the whole body (R5): the event dispatches from inside the `SaveChangesAsync` the handler awaits, so an uncaught exception here would turn into a 500 on `POST /flights` *after* the traveler's tracking write had already committed — an unwind with nothing left to roll back and a response that must still succeed — so a repository or queue failure is logged with the flight id and swallowed, never surfaced.

**A row is queued when unverified, stale, or verified only by `import` — never when it carries an open issue.** `NeedsVerification` queues a row when any of five things is true: `IsVerified` is false; `VerifiedAt` is null; `VerifiedAt` is older than `Verification:StaleAfterDays` (default 180); `VerifiedAt` is more than `FlightTrackedVerificationEventHandler.ClockSkewTolerance` (5 minutes) in the **future**; or `VerificationSource` is `import`. The future-timestamp case exists because CSV import keeps the file's own `VerifiedAt` rather than restamping the moment of import (§6) — without it, an old file imported today would read as freshly verified forever. The 5-minute tolerance only absorbs ordinary clock skew between App Service instances (a row one instance just verified must not be re-queued by a track request landing on another instance a few hundred milliseconds behind) — it stays far short of the imported-row case, which is days or months out. `import` counts as weaker evidence than an automated check for the same reason: a hand-typed CSV is stamped exactly like a source-verified row, so it must not shield a row from the one check that would actually confirm it. R4 beats R3: a row with a non-blank `VerificationIssue` is skipped even when it also looks stale, because an admin is already looking at it and re-queueing would collide with that in-progress state. The open-request skip belongs to `IVerificationQueue.EnqueueAsync` itself, not this handler — it already refuses a key whose entity has an open request (§2.3's unique index) and reports it back as `Skipped`; the handler passes every key it decided on straight through and never pre-filters or duplicates that check.

**Where the spec and the code disagreed (#410).** §4.1 of the design spec described the trigger as "a domain event" as if flight-tracking already raised one — it didn't; `FlightDeleted` and `FlightStatusSynced` did, but nothing fired when a flight was tracked. Rather than call `IVerificationQueue` straight from `TrackFlightCommandHandler`, #410 added `FlightTracked` and a handler for it, keeping the layering CLAUDE.md states elsewhere: the event is Domain, the handler that reacts to it is Application. Separately, the spec's "after `TrackFlightCommand` saves" assumed every track request already reached `SaveChangesAsync` — it didn't: a repeat track that found the traveler already tracking the flight had nothing to write and skipped the save entirely. R1 changed that too, so the save (and the event) now happen unconditionally — the case the trigger mainly exists for, since an already-tracked flight is exactly the one whose reference rows are most likely to have gone stale since the last check.

**§9's rollout is complete.** All ten delivery steps have landed; #410 (step 10, the flight-tracking trigger) was the last.

**`spec/openapi.json` is generated, not hand-authored.** It comes from booting the API host and walking its own route/DTO metadata via Swashbuckle's CLI (`dotnet swagger tofile`, pinned in `.config/dotnet-tools.json`) — regenerate it with `scripts/generate-openapi.sh` from the repo root (the tool manifest is repo-local, so `dotnet swagger` only resolves there; run elsewhere and the dotnet CLI's answer — "You misspelled a built-in dotnet command" — points nowhere near the real cause, which is why the script checks first and says so plainly). The host needs *some* configuration to start — `AeroApiOptions.ApiKey` is `[Required]` and validated on start — so the script boots it on dummy values; the export makes no outbound call and the spec itself carries no configuration values, so a dummy is enough. That block is defined exactly once, inside the script, and both `ci.yml` and `development_flight-assistant-dev-api.yml`'s "Export OpenAPI spec" step call it rather than each keeping a copy. Generation is deterministic — `SwaggerDoc`'s `Version` is a fixed `"v1"`, not a build stamp — which is what lets `ci.yml` regenerate the spec on every PR and fail the build, diff and regenerate command included in the log, if it doesn't match the committed file byte-for-byte; that same check also asserts the regenerated spec contains none of the dummy credential values, since a public-shaped document is exactly where a future leaked example or default would surface. Never hand-edit `spec/openapi.json` — CI will only hand you back a diff, not a fix.

## Conventions

**File layout in Application:**
- Commands: `Application/Commands/{Domain}/{CommandName}.cs` — command record, validator, and handler all in one file.
- Queries: `Application/Queries/{Domain}/{QueryName}.cs` — same pattern.
- Validators: named `{CommandName}Validator`, defined in the same file as the command.
- A format rule shared by more than one validator lives in **one** constant, not two copies of a regex. `Application/Validators/FlightNumberFormat.cs` holds the IATA flight designator pattern used by both `SearchFlightsQueryValidator` and `TrackFlightCommandValidator`, plus a `Description` the Swagger text is rendered from — they had drifted in *both* directions (search accepted an all-digit prefix track refused; track accepted a trailing letter search refused), which is exactly the "search returns a row `POST /flights` rejects" defect the search reshape exists to remove.

**Repository contract:** `SaveChangesAsync()` is called explicitly inside handlers. There is no implicit unit-of-work auto-save.

**External service options:** All external service config uses the Options pattern — `AddOptions<T>().BindConfiguration(section).ValidateOnStart()`.

**Database:**
- Table names: `snake_case` (e.g., `travelers`, `device_tokens`, `traveler_flights`).
- All timestamps: UTC only, suffixed `Utc` (e.g., `CreatedUtc`, `ScheduledDepartureUtc`), stored as `timestamptz`.

**Naming:**
- Commands return a value or `Unit`; queries return data — both are `IRequest<T>`.
- Result/DTO types: `{Name}Result` or `{Name}Dto`.
- Endpoint tag group names match the bounded context (e.g., `"Travelers"`, `"Flights"`).

## Authentication

- JWT Bearer via Azure AD B2C / Entra External ID.
- Traveler identity = `oid` claim (falls back to `sub`), parsed as `Guid`. Use `ClaimsPrincipalExtensions.GetTravelerId()`.
- Scope enforcement: `http.VerifyUserHasAnyAcceptedScope("access_as_user")` at the start of each user-facing handler.
- Admin endpoints use the `"AdminOnly"` authorization policy: authenticated + role claim `"admin"`.
- `TravelerContextMiddleware` enriches Serilog's `LogContext` with TravelerId for every authenticated request.

Set `false` for a local run (`launchSettings.json` does), or it claims requests from the shared dev queue alongside the deployed app and writes audited `system` verifications |
| `Verification:PollInterval` | Optional; default `00:00:30`, range 1 s–1 h |
| `Verification:BatchSize` | Optional; default `10`, range 1–100. How many requests one cycle claims at most |
| `Verification:MaxAttempts` | Optional; default `3`, range 1–10. Source-error attempts a request gets before it completes as `Error` |
| `Verification:IdleRelease` | Optional; default `00:30:00`, range `00:00:00`–`1.00:00:00` (#378). How long a source's downloaded dataset is kept after its last lookup once no open request uses the source; `0` releases it as soon as none does |
| `Verification:StaleAfterDays` | Optional; default `180`, range 1–3650. Not read by the job itself — read by the flight-tracking trigger (#410) to decide whether a row needs re-checking |
| `Verification:DefaultSources:Airport`, `Airline`, `Country` | Optional; defaults `ourairports`, `aeroapi`, `mledoze` — all three now name a registered source (#401; before that, the configured `aeroapi` default would have completed any request that used it straight to `Error`, unregistered). Not read by the job itself, which uses each request's own `sources`, nor by the step-6 admin endpoints, whose `sources` is required and never defaulted — read by the flight-tracking trigger (#410) to build its own `EnqueueAsync` calls |
| `Apns:BundleId`, `Apns:KeyId`, `Apns:TeamId`, `Apns:P8KeyContent` | iOS push; `Apns:UseSandbox=true` for dev |
| `AdminPanel:AllowedOrigin` | CORS origin for admin UI. Code default `http://localhost:5173`; Development sets `http://localhost:5175` to match the panel's Entra redirect URI |
| `GitHub:Token` | Optional; fine-grained, read-only, Actions: read on this repository. Without it `/admin/ci/*` answers 503. Key Vault: `GitHub--Token` |
| `GitHub:Owner`, `GitHub:Repo`, `GitHub:Workflow` | Optional; default `salih1f1`, `flight-assistant-backend`, `ci.yml` |

## Tech Stack

- **.NET 10**, ASP.NET Core Minimal APIs, PostgreSQL 16, Redis
- **Auth:** Azure AD B2C / Entra External ID (JWT Bearer via `Microsoft.Identity.Web`)
- **Cloud:** Azure App Service, Key Vault, Application Insights
- **External APIs:** FlightAware AeroAPI (flight status + search), OpenFlights (reference data seed)
- **Push notifications:** APNs via dotAPNS (iOS only)
- **CI/CD:** GitHub Actions → Azure Web App on push to `development`; EF migration bundle applied before deploy

## Branching

Branch off from `development` for every feature or fix. Open a PR back into `development`. Never commit directly to `development` or `main`.

## Tests

- `FlightAssistant.Domain.Tests` — unit tests for aggregate behavior via factory methods (constructors are private).
- `FlightAssistant.Application.Tests` — handler-level tests.
- `FlightAssistant.Infrastructure.Tests` — repository and interceptor tests; the PostgreSQL-backed ones use the Testcontainers harness (#295) and need Docker running.
- `FlightAssistant.API.Tests` — endpoint integration tests on the InMemory provider. `TestAuthHandler` hardcodes the role claim as lowercase `admin`, so these tests cannot catch a casing mismatch in the real tenant (Entra emits `Admin` on the id token and `admin` on the access token). `FlightAssistantWebApplicationFactory` also gives both verification sources' named clients a transport that throws, so no test can download a dataset.
